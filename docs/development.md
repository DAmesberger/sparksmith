# Development

How Sparksmith is built, checked and driven from the command line. The [README](../README.md) describes the product; this page is for contributors and for anyone scripting it.

PCB design software in Rust, using Solidcraft's egui/wgpu UI and native parametric engine. Component authoring, multi-sheet schematics, PCB layout and production output share one desktop shell. PCB 3D displays physical copper and package models through Solidcraft, with shared selection and whole-net highlighting.

This is an early working editor foundation, not a manufacturing-ready release. See [current evidence and limits](editor-evidence.md).

## Build and run

`rust-toolchain.toml` pins Rust 1.96.0, Clippy, rustfmt and the wasm target. Use rustup, or the Nix dev shell, which provides exactly that toolchain:

```sh
nix develop          # optional: pinned toolchain without rustup
cargo run --locked --profile ci -p sparksmith [FILE.sparksmith]
cargo xtask affected --run   # while iterating: tests of what the change can reach
cargo xtask fast             # before any full CI: format, structural gates, Clippy on changed crates
cargo xtask ci               # once per merge batch
```

The Nix shell builds into `target/nix` unless `CARGO_TARGET_DIR` is already set, and compiles through sccache, which shares compiled crates between worktrees and target directories (paths under each worktree and an absolute target directory are made relative before hashing). The sccache server reads that list when it starts, so after adding a worktree run `sccache --stop-server` once. Set `RUSTC_WRAPPER=` (empty) to build without it. Measured on one Mac, 23 November 2026: `cargo check --workspace --all-targets --profile ci` in a fresh target directory took 182 s without a cache hit and 75 s with a warm cache (100 % Rust hits; binaries, proc macros and incremental workspace crates are not cached).

`cargo xtask affected [--base REV] [--run]` lists the workspace packages a change can affect: those whose folder holds a file changed since REV (default: the merge-base with `main`, plus uncommitted and untracked files), every package that depends on them (from `cargo metadata`, any dependency kind), and the packages whose tests read changed shared data outside their folder, as `xtask/affected.txt` lists them (library data, examples; the toolchain, the lock file and the workspace manifest select the whole workspace). `--run` runs `cargo test --profile ci` on exactly those. `cargo xtask fast [--base REV]` runs `cargo fmt --check`, the structural gates (layers, core-modules, connectivity, copper-source, f64-lengths, generic-terms, no-builtin-data, clean-room, brand-crates, ui-containers, ui-forms, raw-keys, and licences when `Cargo.lock` changed), strict Clippy on the changed packages only, and `surface --check` when the automation crate is affected; it prints one line per gate and stops after the first class that fails. Neither replaces `cargo xtask ci`: it runs once per merge batch, and hosted CI runs it again on push. The order is in [verification](../skills/sparksmith-verification/SKILL.md#which-gate-when).

The app starts with an empty project (as File › New does); open a project, or write the showcase with the CLI below. Component authoring includes Symbol, Footprint, Mapping and 3D modes; each finished edit of the five component drafts (component, symbol, package, footprint, binding) is one undo step, and Publish creates immutable project revisions. In Schematic, Place (or P) opens the Place palette: type a query such as `10k 0603`, `res>=10k` or `tol<=1%`, move with ↑/↓, press Enter to place (Shift+Enter keeps the palette open) or click a row to place it with the mouse; the properties card previews the highlighted part. Connect terminals with Wire and rename a selected wire's net. The Browser's Components section has a filter field that uses the same search. In PCB, preview/apply Update PCB, move placements and route between pads. Switch between 2D and 3D within PCB; selection and whole-net highlighting are shared.

File offers New, Open, Save, Save as and Export to Solidcraft through native dialogs; reads, writes and exports run in the background. Unsaved work is snapshotted for crash recovery and offered at the next launch. Project files contain the revisioned library snapshot and the definition drafts, so they reopen offline. Native export writes a new parametric `.solidcraft` file; package models are clearly identified envelopes.

Per-user files (settings, keymap, fab and AI profiles, live-MCP tokens) live in the config folder `sparksmith` (`~/Library/Application Support/sparksmith`, `%APPDATA%\sparksmith`, `$XDG_CONFIG_HOME/sparksmith` or `~/.config/sparksmith`), the library index cache in the platform cache folder `sparksmith`, and recovery snapshots in `~/Library/Application Support/Sparksmith/Recovery`, `%LOCALAPPDATA%\Sparksmith\Recovery` or `$XDG_STATE_HOME/sparksmith/recovery`. `SPARKSMITH_CONFIG_DIR`, `SPARKSMITH_CACHE_DIR` and `SPARKSMITH_RECOVERY_DIR` move them. The names come from `sparksmith_core::product`. On the first start after the rename from Pcbcraft, the app and the CLI copy the former `pcbcraft` config folder and `Pcbcraft`/`pcbcraft` recovery folder to the new names when the new folder does not exist yet; the former folders are kept unchanged and the cache is rebuilt ([rename](rename-phase-b.md)).

`cargo xtask package` makes the download for the system it runs on ([packages](packages.md)).

`nix develop .#windows -c cargo xtask windows-check [-p PACKAGE]...` is strict Clippy of the workspace, tests included, for Windows on a machine that is not one (Linux; not tried on macOS). The shell adds the `x86_64-pc-windows-gnu` target and a MinGW C compiler for the dependencies' build scripts. It type-checks and lints what `cfg(windows)` and `cfg(not(unix))` compile; it links and runs nothing, and `cfg(target_env = "msvc")` is not seen. Run it before every push: hosted Windows takes hours to say the same. Measured on one Linux machine with other builds running, 25 November 2026: 8 min 42 s into an empty target folder, 1 min after a change in the core.

Hosted CI (`.github/workflows/ci.yml`) runs `cargo xtask ci` on Linux for every push and pull request, and on Windows for pushes to `main` and manual runs. There is no macOS job: the native open, save and quit lifecycle on macOS is checked only by hand runs in the macOS VM (the e2e run notes in this folder), not by CI. This is a known gap.

Navigation: scroll zooms; middle-drag pans; right-drag orbits in 3D. Cmd/Ctrl+S saves, +Shift+S saves as, +O opens, +N starts a new project, +Z/+Shift+Z undo and redo.

## Architecture

| Crate | Responsibility |
| --- | --- |
| `sparksmith-core` | Pure, wasm-compatible document: revisioned library definitions and drafts, component instances and symbol occurrences, schematic, persistent nets, layout, impact plans, completeness findings, typed `Operation`s and `Query`s, the one `Engine` (shared undo, engine-owned drafts), file format, typed errors and check findings. |
| `sparksmith-io` | Bounded reads, atomic writes, crash recovery. |
| `sparksmith-solidcraft` | Builds the native Solidcraft model through a typed facade over Solidcraft's command API. |
| `sparksmith-kicad` | KiCad board import, slice K1: footprints, pads (every shape, custom pads, mask, paste and drills) and their placement, built into a new project through the one engine, with an import report of what is exact, approximated, reported or refused. It reads the bytes it is given. |
| `sparksmith-fabcheck` | Production files read back: the core ships it (`fabrication::readback`, the check before every export), other crates use it as a dev-dependency, and `xtask`: CSV, PDF, Gerber and Excellon readers, exact polygon comparison in integer nanometres (difference area, widest piece), drill-hit pairing, and `kicad-cli` run as a black-box oracle on a temporary copy. |
| `sparksmith-firmware` | Pin-configuration exports from the core's pin report (JSON, C header, Zephyr overlay skeleton, Rust constants); pure text, beside `sparksmith-io`. |
| `sparksmith-automation` | Headless `Session` (engine + open/save/export) shared by the JSON-lines transport and the MCP server, and the live channel into the open window ([live MCP](#live-mcp)). |
| `sparksmith-assist` | The datasheet assistant: a tool loop over the automation session that drafts a part from its datasheets, on a model you configure (Anthropic Messages or any OpenAI-compatible endpoint, hosted or local), with token, time and request caps ([as built](datasheet-assistant.md)). |
| `sparksmith-ui` | The UI toolkit the desktop draws with, seeded from SolidCraft's MIT/Apache interface code (UI kit, theme tokens, icons, fonts) as of `a34756830` (see [attribution](../ATTRIBUTION.md#the-ui-toolkit-seed-cratesui)). |
| `sparksmith`, `sparksmith-cli` | Desktop editor and command line (its binary is `sparksmith`). |

`cargo xtask layers` enforces this direction; `cargo xtask ui-containers` rejects raw egui windows, areas and panels outside the kit's `ui_kit::Container` (SolidCraft's, vendored in `crates/ui`). `cargo xtask core-modules` enforces the core module map in [component model](component-model.md), and `cargo xtask connectivity` that only `layout/connectivity` decides whether copper joins ([copper graph](copper-graph.md#where-connectivity-lives)). `cargo xtask copper-source` rejects copper geometry Layout would derive on its own (track and pad outlines, a fill's stored copper, a via's pad size): it draws the board plan's copper only, as the 3D view meshes it ([board plan and interface](architecture/board-plan-and-interface.md#one-copper-source-for-2d-and-3d)); `cargo xtask board-parity` runs it too. `cargo xtask f64-lengths` rejects new serialized `f64` length fields in the core's `model`, `library` and `geometry` modules: stored lengths are `units::Nm`; its allow-list holds the fields the units migration has yet to convert, and only shrinks. `cargo xtask licences --check` rejects dependencies that require GPL-family or unreviewed licenses, `cargo xtask brand-crates` rejects SolidCraft's brand-licensed crates (`solidcraft-ui-kit`, `solidcraft-look`, `solidcraft-theme`) and `solidcraft-ui-egui` anywhere in the dependency graph, and `cargo xtask clean-room` rejects EDA library files and data in the repository. `cargo xtask no-builtin-data` (alias `no-builtin-parts`) rejects `include_str!` and `include_bytes!` in non-test program code, except the interface assets and the MCP skill prompt ([generator plugins](generator-plugins.md#gate-no-built-in-data)); library data ships in `library/`. `cargo xtask generic-terms` rejects product-specific words for a linked design (an example use case, such as an enclosure) in any path or text file under `crates/`, `apps/` and `xtask/`; it has no allow-list, and such examples belong in prose under `docs/`. All of these run in `cargo xtask ci`.

## File versions

The project file carries a format `version` (`sparksmith_core::format::FILE_VERSION`). The project tree that replaces the single document, its two layouts and its encoding rules are specified in [the file format](file-format.md).

Until the first release the file format is version 1 and Sparksmith keeps no backward compatibility: a stored-type change edits version 1 in place, older files are refused, and the examples are regenerated. A file of any other version is refused, naming its version and the one this build reads. From the first release on, every incompatible change raises `FILE_VERSION` and adds a converter step.

- **Golden file.** `crates/io/tests/fixtures/format/demo.sparksmith` (the demo design with its library and open drafts) opens and saves byte for byte (`the_golden_project_opens_and_saves_byte_for_byte` in `sparksmith-io`). A stored-type change writes it again.
- **Examples.** For a stored-type change, rewrite the five component examples and the IO golden through the project reader and writer. Run `SPARKSMITH_WRITE_EXAMPLE=1 cargo test -p sparksmith-io --test example_files regenerate_stored_project_fixtures -- --ignored --exact`. This preserves each file’s existing project identity, including the unassigned module template used as input to the dev board.
- **Dev board.** Run `sh examples/esp32-s31-devboard/regenerate.sh` with the built CLI. After a shipped generator changes, add `--rebase` to carry the recorded edits onto the new generation first. The replay regenerates the board, manufacturing files and schematic PDF together. [Board replay](../examples/esp32-s31-devboard/README.md)

## CLI, JSON lines and MCP

```sh
cargo run --locked --profile ci -p sparksmith-cli -- showcase example.sparksmith   # a routed 4-layer board with via examples; open it in the app
cargo run --locked --profile ci -p sparksmith-cli -- parts parts.sparksmith   # 24 invented EX- parts for the Place palette
cargo run --locked --profile ci -p sparksmith-cli -- sample-library NEW_DIR [NAME]   # the same catalog as a library folder
cargo run --locked --profile ci -p sparksmith-cli -- export example.sparksmith example.solidcraft
cargo run --locked --profile ci -p sparksmith-cli -- fab example.sparksmith out/   # production check, then Gerber X2, Excellon, job, pick-and-place, BOM and PDF drawings
cargo run --locked --profile ci -p sparksmith-cli -- export-schematic-pdf example.sparksmith example.pdf [--sheet ID]...   # vector PDF, one page per sheet
cargo run --locked --profile ci -p sparksmith-cli -- check-bodies example.sparksmith [--all]   # each placed 3D body's lead contacts against its pads on the board (board.body_off_pads)
cargo run --locked --profile ci -p sparksmith-cli -- commands
cargo run --locked --profile ci -p sparksmith-cli -- stdio [--permission-mode MODE] [--allow-folder DIR]... [FILE.sparksmith]
cargo run --locked --profile ci -p sparksmith-cli -- stdio --operator [FILE.sparksmith]
cargo run --locked --profile ci -p sparksmith-cli -- mcp [--permission-mode MODE] [--allow-folder DIR]... [--wire-log NEW_FILE] [FILE.sparksmith]
cargo run --locked --profile ci -p sparksmith-cli -- mcp --live [--port PORT] [--wire-log NEW_FILE]   # the project open in the desktop window
cargo run --locked --profile ci -p sparksmith-cli -- mcp-replay WIRE.jsonl NEW_REPLAY.jsonl [--root DIR] [--session N]   # a recorded MCP run as a stdio replay
ANTHROPIC_API_KEY=… cargo run --locked --profile ci -p sparksmith-cli -- design-part \
  --datasheet PART.pdf --name PART --out part.sparksmith   # drafts + PART.review.md; publishes nothing
cargo run --locked --profile ci -p sparksmith-cli -- design-part --provider openai \
  --base-url http://localhost:11434/v1 --model MODEL --context-tokens N --vision yes \
  --datasheet PART.pdf --name PART --out part.sparksmith   # the same on a local model
cargo run --locked --profile ci -p sparksmith-cli -- design-body --project BOARD.sparksmith \
  --designator J16 --datasheet PART.pdf [--photo URL]... --out board-2.sparksmith   # a placed part's 3D body from its datasheet, footprint kept
```

`stdio` reads one JSON request per line (4 MiB maximum) and answers `{"ok":true,"result":…}` or `{"ok":false,"error":{"code":…,"message":…}}`. `project.apply` takes the same typed operations as the UI with an expected revision; `project.inspect`, `.undo`, `.redo`, `.new`, `.open`, `.save`, `.preview_update`, `.apply_update` and `.export_native` share the session. `mcp` serves the same catalog over stdio as MCP `2026-07-28` (only that version; a client that sends `initialize` is told so): six verbs, `find`, `describe`, `query`, `apply`, `act` and `show`, carry every entry by name, as the [MCP surface](mcp-surface.md#as-built-s3-the-cut-over-14-november-2026) describes. `commands` prints schemas generated from the Rust types.

For a named entry, the JSON-lines `project.schema` match includes its parameter schema in `schema` and its successful result schema in `reply`. Pass the exact key from `reply.more_defs` as `def` to retrieve a deferred output definition. MCP `describe` also gives `call_reply_entry` for its suggested invocation. A one-step MCP document edit goes through `project.apply_all` and returns an `outcomes` array. Successful MCP project calls add the handle in `project` when the entry has no field with that name.

Replies on both are compact: a mutation answers with `revision`, `outcome`, `changes` (added, changed and removed stable ids by collection, such as `{"added":{"vias":[644]}}`), `findings` (the new ones, resolved counts per code, the open total) and the changed `drafts`. `project.inspect` answers with counts, drafts and findings per code, and with `at` (a JSON pointer such as `/project/nets`) reads one piece of the document. `verbose: true`, beside `command` or inside `params`, returns the whole snapshot instead. In MCP, `tools/list` is the six verbs and nothing else (3,398 bytes, held under 3.5 KB by a test); `find {text}` names the entries that do something and `describe {name}` returns one's exact schema and the verb call that sends it (`project.schema` on JSON lines). `prompts/list` offers the workflows: `datasheet_to_component` (arguments `part`, `datasheets`, `notes`) is the [datasheet-to-component workflow](datasheet-assistant.md#mcp-workflow), served from `skills/sparksmith-datasheet-part/SKILL.md`.

Every command has a permission class: read, edit, ask or never, shown by `find` and `describe` and in `project.schema`. The front door (`Surface::call`) enforces the class for every model-facing transport (headless MCP, live MCP and `stdio`): the never class is always refused (over MCP it is not even in the catalog a model finds), and so is a path outside the run's folders. `mcp` and `stdio` are gated alike, because Sparksmith cannot tell a script from a model; `--permission-mode` chooses how: `ask-every-time` runs only reads, `auto-allow-edits` (the default) also runs edits, and `allow-all` runs everything except the never class. Neither has a way to ask, so whatever would need a person is refused with `gate.needs_person` and a message saying how to run it where a person can allow it; `--permission-mode allow-all` is the operator's explicit choice to let ask-class requests run. Under any mode, a path must be absolute and inside an `--allow-folder` or the folder of the project named on the command line. `stdio --operator` says you are running it yourself, not a model: every class runs, including the never class (favourites), with any path, as at the command line. It takes no mode or folders, and `mcp` does not accept it. Your own replays use it (`examples/esp32-s31-devboard/regenerate.sh`).

### Recording and replaying an MCP run

`mcp --wire-log NEW_FILE` writes the wire log of a run: every line the server reads from its client and every line it writes back, byte for byte, with its direction, its order and the server's clock. It is off unless asked for, refuses a file that exists, and works for the headless server and for `mcp --live`. It sits on the server's own pipes, so it shows what the client sent and what it was answered, and changes neither. If a row cannot be written the server stops instead of serving a message it did not record.

- **Format.** JSON lines. The first row is `{"record":"start","format":1,…}` with the server's name and version, the protocol, the permission mode, the allowed folders and the project file the server was started on (`live` for the window). The server takes no key, and no environment variable is written. Every other row is `{"record":"in"|"out","n":N,"t_ms":T,"text":"…"}`: `in` is from the client, `n` counts from 1 in the order the server saw the lines, `t_ms` is milliseconds since 1970-01-01 UTC, and `text` is the line without its newline. Bytes that are not UTF-8 are in `hex` instead of `text`. `"nl":false` marks bytes no newline followed: a piece of a line over 4 MiB, which the next row of that direction continues, or what a pipe held when it closed. Each direction's rows in order, with a newline after every row but those, are that direction's exact bytes.
- **Refusals are in it.** A call the gate refuses is a request row and an answer row like any other, so a `gate.needs_person` answer is the record of a gate request.
- **Where to put it.** Outside the folders the client may write (`--allow-folder`). A client allowed to write a folder can replace a file in it.

`mcp-replay WIRE.jsonl NEW_REPLAY.jsonl [--root DIR] [--session N]` turns a wire log into an engine replay: the JSON-lines requests that rebuild the project through `stdio --operator`, with no model. Run it with the build that served the run, because it maps each call with that build's own verbs.

- **Kept:** every accepted call that changes something. That is each `apply`, each `act` (saves, exports, publishing, `project.new`, `project.open`) and the reads that hold session state a later call builds on (`assist.pinout_edit` and `assist.pinout_preview`, which `assist.pinout_apply` imports from).
- **Dropped:** refused and failed calls, dry runs, every other read, and `find`, `describe` and `show`.
- **Paths** inside the run's folder come out relative to it. The folder is `--root`, or the one folder the wire log's first row names.
- **Stops, naming the call,** on anything it cannot map: an accepted call this build does not read, a kept call without an answer, a revision the kept calls do not explain (something outside the record changed the project), a path outside the folder, or a call that builds on what a refused call left behind. It writes nothing then, and never replaces a file.
- **One replay is one project.** The server holds several projects; `stdio` holds one. For a run that changed several, convert each with `--session N` (counted in the order the run first used them) and replay them in the order the run saved them.
- **Summary.** It prints what it kept and dropped as JSON: the counts, the refusals by code, the gate requests (`needs_person`) and the paths the replay names.

To replay, start in a folder that holds the files the replay reads and the folders it writes into (the summary's `paths`), and check that no reply is a refusal:

```sh
sparksmith stdio --operator < replay.jsonl > replies.jsonl
grep -c '"ok":false' replies.jsonl        # must print 0
sparksmith fab board.sparksmith fab/ --date none
```

`apps/sparksmith-cli/tests/run_record.rs` proves the chain without a model: a scripted client builds a small board over the real transport, and the replay saves a byte-identical project and fabrication files with the same release revision.

`mcp-replay --transcript` reads a client's own transcript instead (Claude Code's `stream-json`, as in `examples/*-mcp-1/`). A transcript has the calls and whether each failed, but it is not the wire: it has no first row, so `--root` is needed, and a result it cut hides the revision the converter checks. Use it for runs recorded before the wire log existed.

### Live MCP

An assistant can also edit the project open in the desktop window, so you watch each change and share one undo history. In Sparksmith, choose **Help › Connect AI assistants…** (also in the in-window File menu and the command palette) and turn on **Let AI assistants edit this project**. It is off at every start. The window shows the configuration to copy:

```json
{"mcpServers": {"sparksmith": {"command": "/path/to/sparksmith", "args": ["mcp", "--live"]}}}
```

For Claude Code: `claude mcp add sparksmith -- /path/to/sparksmith mcp --live`.

- **Connection.** The window listens on `127.0.0.1` only, from port 27979 (or the next free one), using Solidcraft's control channel. Each time you turn it on, it makes a new token and writes it to `control/PORT.token` in the Sparksmith config folder, readable only by you; `control/current.port` names the port. `sparksmith mcp --live [--port PORT]` reads both, so the configuration holds no secret. `SPARKSMITH_CONTROL_TOKEN` gives a token explicitly. Turning access off, or closing the window, closes every connection and removes the files.
- **Same engine.** `mcp --live` serves the same six verbs as the headless server and sends each call over the channel as one envelope (`surface.call`: `entry`, `params`, `expected_revision`, `dry_run`). The window runs it on the UI thread, between frames, through the same front door (`Surface::call`), on its own engine. Opening, saving and starting projects stay yours: the window grants an assistant every module but `files`, so those are refused with `gate.module`. Replies stay compact: a via placed on the demo answers in under 4 KB.
- **Revisions.** Every call that changes the project names `expected_revision` (the `apply` verb requires it; `act` takes it for an action that changes the document). A stale revision is refused with `stale_revision`, so the assistant reads again.
- **Refusals.** While you type in a field, drag, or have a menu, the command palette, a file question or an update review open, a change is refused with `live.busy` and the reason. Reads and dry runs still answer.
- **Permissions.** The window's choice (reading only; reading and edits, the default; or everything except settings) decides as `--permission-mode` does. A call that needs a person, such as an export, waits for **Allow** or **Deny** in the window; the never class is refused. Paths must lie in your home folder, the temporary folder or the project's folder.
- **Clients.** The server speaks MCP `2026-07-28` only. Claude Code connects as it is; Codex needs its `mcp_2026_07_28` feature and `CODEX_MCP_PROTOCOL_VERSION=2026-07-28`; OpenCode needs `"protocol": "2026-07-28"` on the server in its own configuration. Clients that speak only older versions (VS Code, Zed, Gemini CLI today) cannot connect ([who can connect](mcp-surface.md#13-who-can-connect-to-a-2026-07-28-only-server-today)).
- **What you see.** The application bar shows *AI access on* or *AI assistant connected* while access is on; its × turns access off. Each assistant edit shows as a toast with Undo and a Messages line (*AI assistant edit: layout.add_via*), and undoing one says *Undid AI assistant edit*.

`project.query` also answers the parts catalog ([design and query language](parts-library.md)): `library.search` ranks the project's component lineages for a one-line query, `library.facets` lists the fields, packages and badges the matches carry, and `library.inspect` reports one revision. For example:

```json
{"command":"project.query","params":{"query":"library.search","params":{"query":"res>=10k pkg:0603","limit":10}}}
```

Field keys come from the project's field names and units, so a query reports `V>=10k: 10 k has no unit of voltage` rather than guessing.

Library folders ([S3](parts-library.md#s3-as-built)) are plain directories of immutable revision files, shareable through git. `library.source.create` makes a new one and `library.source.add` lists an existing one in the user's settings (`SPARKSMITH_CONFIG_DIR`, `SPARKSMITH_CACHE_DIR` override the platform directories; `library.source.remove` and `.enable` change the list). They are ask-class actions: they change the person's settings and files, so a model runs them only after a person's Allow (or under `allow-all`), on a folder inside the run's folders; `library.search` then includes its entries, `library.place_from_folder` imports and places in one undo step and `library.publish_to_folder` promotes a project revision to a writable folder. Imported revisions keep their origin and attached copies, so projects reopen without the folder. `library.import_from_project` copies one published revision and its closure from another `.sparksmith` file, as one undo step.

## Board parity

The board's flat bodies (laminate slabs, pad, track, via and fill copper) are described once by the board plan (`sparksmith_solidcraft::project::plan`): each body's kind, source object, layer, z span, outline loops and look, as pure data read from the document. The exact native build makes each of them from the plan. `cargo xtask board-parity` builds every example board under `examples/` and checks, body by body:

- the build against the plan by geometry fit (`plan::parity`, slice G1): each planned body built once, of its kind, source and layer; its top and bottom faces, read from the B-rep's face loops (each edge's own curve sampled to 0.1 µm, `project::fit`), against the plan's loops flattened to the same tolerance: the exact area where they differ (their symmetric difference on a nanometre grid) no more than their length times both tolerances, every point within 1 µm of the other outline, and the same number of holes; its heights within 1 µm; and, for copper, its volume within 1 ppm as one more sign. Laminate slabs are checked by outline like copper (their holes may cross, as a via ring through a track's cut in a foil level: the plan's loops nest by containment, crossing holes uniting). No flat body may be built that the plan lacks. Measured on the ESP32-S31 example (`export_tiers`, 13 November 2026, loaded machine): every outline within 0.102 µm of its plan, at most 0.0096 mm² between them on a whole slab; the check took 2.3 s of a 14.6 s mechanical export and 9.5 s of a 36.3 s full one;
- every native body against the record in `crates/automation/tests/board_parity/<board>.jsonl` (box to 1 nm, volume to 1 ppm), made from the build before the plan existed.

- the live view's meshes against the plan (`mesh::parity`, `example_boards_mesh_as_their_plan`): one mesh per plan body, of its kind, source and layer, the laminate drawn whole (`BoardPlan::whole_laminate`); each box within the flattening tolerance (2 µm), each volume exact on its flattened loops (1 ppb) and within flattening (loop length × 2 µm × thickness) of the plan body's exact volume. It needs no build, so the workspace tests run it too.

A change meant to change the built bodies rewrites the records with `SPARKSMITH_BLESS_PARITY=1 cargo xtask board-parity`; say so in its commit. CI runs the exact-build check once, after the workspace tests, which leave it out (it is an ignored test).

The 3D view always uses the direct mesh (`Flat::Meshed`; stage A4 removed the setting and the live native board): no design of the board is made. The flat bodies are meshed from the plan (`project::mesh`, with a per-body memo), and each part is its package revision's own Solidcraft design (`project::designs`), evaluated once, kept between models and shared by every placement, drawn where the document's transform puts it (`interface::package::model_to_board`). The model worker keeps the last model only and makes every next board (an edit, an undo or redo, a refill) from what it kept (`project::update`). A meshed model is never saved; exports build the exact model, which is never updated in place. `cargo xtask board-parity` also checks every example board's parts in the live model against the exact build's solved joints (`designs::parity`: every vertex within 1 µm); the workspace tests check every kind of part model on both sides at every turn (`project::designs::tests`).

**Exports (stage A5).** `sparksmith_solidcraft::export::board` is the one export of the exact board: File › Export to SolidCraft…, `project.export_native {path, tier?}` and `sparksmith-cli export FILE NEW_FILE [--tier mechanical|full]` all call it. Tier `mechanical` (the default) is the laminate, the pads and the parts; `full` adds every track, via and fill; `interface` is published only (`interface.publish`). A board whose outline is invalid is refused (`export.outline_invalid`). The build counts each Solidcraft command on an `export::Watch` and says its stage (building, evaluating, checking, saving); `Watch::cancel` stops it at the next command or checked body with `Cancelled`, writing nothing (the board's evaluation and native serialization run to their end first; staged output that finishes after cancellation is removed). Before writing, every flat body is checked against the board plan the build read by geometry fit (`plan::check`, the same comparison as `plan::parity`, slice G1). A model that does not fit is refused by default and nothing is written: `Error::Unfit`, code `export_unfit`, whose message names each body in the user's words ("Track 12 on the top layer: its track copper was built in another shape: its outline is off by up to 0.0500 mm (0.1000 mm² differs)"; a slab is "The laminate from z 0.165 to 0.200 mm", with its holes counted where they differ). `project.export_native {write_anyway: true}`, `sparksmith-cli export … --write-anyway` and the window's "Write the file even if bodies do not fit the board" (off each time it opens) write it all the same; the report then lists each body planned and not built, or built and not planned, with its object, kind, layer, box, volume and fit (`check.differences[].fit`: difference area, deviation, holes, heights), and `check.max_deviation_mm` and `check.max_area_mm2` say how close the bodies that fit came. The host writes a hidden sibling and publishes it through the IO layer’s create-only primitive, so a competing creator’s file is never replaced. Native save and export APIs take `native::files::NewFile` from `sparksmith_automation::native_files::new_file`; Solidcraft’s public container serializer keeps the final design name and rebases links against the final directory, before the bytes reach the staging path. The shared host uses `persistence::StagedNew`, which keeps native errors intact and reports a directory-sync failure after publication as `written_unsynced`. A mechanical or full `interface.publish` reports the same check for its section 2 (`published.check`) and writes its files all the same. In the app the export runs on its own thread, so saving, recovery and editing go on; its window shows the stage, the commands run and Stop. `cargo test -p sparksmith-automation --profile ci --test export_tiers -- --ignored --nocapture` measures both tiers on the ESP32-S31 example.

## Random boards

`fabrication::tests::random` (in `sparksmith-core`) draws small legal boards from a seed, edits them at random and checks every rule below after each edit, whatever the board. A seed is the same board on every machine: the generator is its own, and nothing reads a clock or the order of a hash map.

A board has 2, 4 or 6 layers (the seed's remainder by three) and any of: pads of every shape, kind and turn, parts on both sides with turned datums, copper net ties, text and legend, curved outlines, windows, slots and holes, net classes and clearance overrides, a differential pair, tracks, vias (tented, open, filled and capped), planes, drawn and hatched fills, pad fill overrides, keepouts. Tracks are straight in the document, so an arc is a run of chords. The edits are the engine's own commands (place, move, flip, route, shove, drag, change layer, route a pair, delete, lock, pour, pad overrides, refill, rules, the board's shape, undo, redo, save and reopen, paste) and some that must be refused. A pasted part is a symbol that is not on the board until it is placed. The sketch engine is the host's: a stand-in (`outline.rs`) keeps the board as text and makes it larger, cuts a window in it, or opens its outline; what the board makes of the solve is the product's.

| Rule | What must hold |
|---|---|
| `Reopen` | Saved and opened, the document is the document, its file is the same bytes, and its fills fill alike |
| `History` | Undo gives the state before, redo the state after (but for the counters of the board's interface, which never go back) |
| `Refusal` | A refused edit changes nothing: document, revision, undo and redo |
| `Cache` | The engine's copper graph and issues are those made afresh |
| `Connectivity` | The graph joins the pads that copper joins, and no others; an open net has a finding and an airwire; a part not on the board has a finding |
| `Silent` | No edit but a deletion leaves a net fewer vias without its report or an open-net finding naming the net, and no edit changes the netlist of a net that was there |
| `Short` | Copper of two nets that overlaps is a finding no waiver accepts |
| `Close` | Pads, tracks and vias of two nets nearer than the rules allow are a finding naming both, measured again |
| `Blocks` | Every error of the board checks, and everything unrouted, unplaced or stale, blocks the production check |
| `Outline` | A board without a valid outline gives no files |
| `Stale` | A fill is what the board gives now, or told as stale |
| `Island` | A fill that removes islands has those that reach a pad, via or track of its net, through the net's other fills if need be, and no others |
| `Clearance` | Every fill keeps every clearance, the edge, cutouts, keepouts and its own outline, measured between segments |
| `ReadBack` | The check before every export passes |
| `Image` | `fabcheck`'s pictures of the copper, mask, paste and drill files are those painted from the document |
| `Inventory` | Read back through `fabcheck`, the files list every hole, via and track once, with place, size and net, and every pad on its layers |

`truth.rs` works out what is on the board from the document again, as plain polygons, with none of the production geometry, the copper graph, the polygon library or the point oracle of the export check. It shares the document, the stored fill regions, the footprint a part resolves to, and the effective mask expansion and paste reduction. `ReadBack` is the product's own check, and `Stale` computes the fills with the product's own code: it tells a wrong key, not a wrong fill.

**Runs.** Twelve fixed seeds run with the other tests. A long run names its seeds, `first..last`; it can be split by range over several processes:

```sh
SPARKSMITH_RANDOM_BOARDS=1000..2000 cargo test -p sparksmith-core --lib random::the_boards -- --nocapture
```

A failure names the rules broken, the seed and the least part of it that still breaks one of them, and the command to run that again:

```sh
SPARKSMITH_RANDOM_CASE='17:0-3,9,22' cargo test -p sparksmith-core --lib random::the_named_case -- --nocapture
```

The numbers are places in the seed's list of atoms: a change to the generator (`plan.rs`) makes other boards of the same seeds, so a case worth keeping becomes a test of its own.

By hand on GitHub: the workflow *Random boards* (`.github/workflows/random-boards.yml`) takes a range, or 200 seeds that go by its run number. It has no schedule.

**Alive.** `every_seeded_fault_is_told_by_the_rules_that_must_tell_it` makes what was seen of one board wrong in 24 ways (a fill clearance, a drill position, a mirrored mask, a lost via, old copper and an old graph among them) and names the rules that must tell each. `the_generator_makes_everything_and_most_edits_are_taken` keeps the boards from being empty.

## KiCad import comparison

`sparksmith import-kicad DIR|FILE.kicad_pcb|FILE.kicad_pro NEW_FILE.sparksmith [--profile ID]` imports a KiCad board (a folder names its one board, a `.kicad_pro` the board of its name; the `.kicad_pro` is read when present) through the one command engine with SolidCraft's sketch engines, on `--profile`'s profile from the fab profile library, else the one a new board takes ([new boards](board-rules-and-shape.md#fab-profile-files)), and saves it. It prints the import report's counts, with each KiCad rule looser than the fab profile named under its count with both values ("min drill: KiCad 0.05 mm, fab profile 0.1 mm (min_through_hole_diameter)", also `looser_rules`), and writes its detail (designators, pads, net names, the rules not taken) beside the new file as `NEW_FILE.kicad-import.json`. A file never holds fill copper: it is derivable, and refilled on open. The desktop app runs the same import (`sparksmith_automation::kicad_import`) from File › Import KiCad project… (also in the command palette) and for a `.kicad_pro` or `.kicad_pcb` opened from Finder: off the window's thread, it opens the result as an unsaved project, a document to start from with no undo steps, as an opened file, whose first save proposes the KiCad project's folder and name, and shows the report in a window that the palette or Window › KiCad Import Report reopens while the project is open. Imported components and footprints take their KiCad footprint's name without its library nickname (`R_0805` of `Library:R_0805`), without control characters and with whitespace runs made one space; the full KiCad id stays in each definition's provenance ("KiCad footprint: Library:R_0805"). Two footprints whose names come out equal (two libraries' `R_0805`, or one footprint whose copies differ) are numbered apart (`R_0805, 2`), and the report counts names changed and names numbered apart. Copies of one KiCad footprint with equal pads share them, and distinct KiCad footprints never do, however alike their pads. Each part's KiCad Value (the schematic's, else the footprint's) becomes its part's typed fields, parsed by the core as a value typed into a palette part is: the whole text into the first field that takes it, else each word (split at spaces, `/`, `,` and parentheses, so `2k(1%)` is `2k` and `1%`) into the first free field that takes it (a resistor's "4k7" is its Resistance, a capacitor's "100n 16V" its Capacitance and Rated voltage); the report counts parts whose value set fields, values with words no field took, and values whose part selects no value field. A part number (a property named `MPN`, `Manufacturer Part Number`, `MFR PN`, `Part Number` and the like, any case, spaces, `_` and `-` ignored) with a manufacturer (`Manufacturer`, `MFR`, `Manf`) becomes the placed part's manufacturer part (`instance.assign_part`); one without a manufacturer is counted, never given an invented one. Tracks and vias come in as the file has them (`layout::import_copper`, outside the routing commands, which keep the rules): none is left out for breaking a rule or touching another net's copper, and the board checks report those. Only what a document cannot hold is left out and listed: copper off the board, a via without a ring or not through, a width outside 0.05–5 mm. Such a track piece is recorded in the project (`layout.set_refused_import_tracks`), so copper it left ending in nothing says so in its finding ("Track on VIN (Top) stops at (10, 10) mm: import refused the rest (outside the board)"); the person deletes it or routes on.

`cargo xtask kicad-compare --design PATH` (or `SPARKSMITH_KICAD_DESIGN`) imports every `.kicad_pcb` of a design, writes our fabrication files and compares their copper (pads, tracks, vias and zone fills; KiCad's copper drawings are left out), mask, paste and drill hits with KiCad's own plots to 1 µm (drill hits to 1 µm plus the √2 µm two files written to 1 µm may round apart), and the board outline we emit with KiCad’s `Edge.Cuts` plot (the contours both profile layers draw, paired one to one and compared both ways; a missing plot of either and a contour only one draws fail, so a cutout we write as a plated slot, a drill hit, fails as missing from our profile). The gates never build Solidcraft, so run it as `cargo run -p xtask --features sketch -- kicad-compare …` to import the outline as a board sketch, as the CLI and the app do; without the feature the outline is the rectangle around it. Our board origin is the outline's lower-left corner, in whole micrometres (our outlines lie right of and above the origin), so KiCad's plots, taken about the drill and place origin, are moved onto ours before comparing. Nets come from the schematic when the board’s folder holds its root `.kicad_sch` (the board’s stem) and, inside that folder, the sheet files the sheets name (from the folder itself or from the naming sheet’s; a name both hold is not chosen between, and the schematic is reported unreadable; `kicad-compare` itself reads only the schematics directly in the folder): each sheet instance becomes a sheet under a sheet symbol with its pins; each footprint's part gets a symbol with KiCad's units, body and pins where KiCad has them (a pad no pin names, an unmapped pad, gets a visible pin on the body's right side marked "added by import" and an "unmapped pad" finding, counted; the person keeps it by clearing the mark in the pin's card or waiving the finding, or moves or deletes it), placed and turned where KiCad has it; then KiCad's wires (with their corners, joining where KiCad joins them), junctions, labels, power symbols, hidden power inputs and no-connect flags are drawn with the schematic commands. A schematic part the board has no footprint of (a partly laid out project) comes in as a part of its KiCad symbol alone, a terminal per pin number, placed and wired where KiCad has it with no footprint chosen; Issues lists it as having no footprint once the project is saved and reopened, and the import report names it. A net-tie footprint imports as one component. Each declared pad group becomes an independent copper tie with its own ends and bridges. Solid lines, three-point arcs, circles, rectangles and polygon drawings contribute their stroked or filled copper on the declared side. Their curved edges become chords. Dashed strokes, visible text on copper, and bridge outlines with holes require review. The report names the footprint and asks for each tie’s purpose. If the groups overlap, a bridge crosses groups, or the drawings cannot connect the declared ends, the pads keep their individual nets and the report explains which ties need review. A JP reference on a part with two or more lands and no source model suggests reviewing it as a solder jumper. Our stackup holds one solder mask thickness for both sides: where KiCad's differ, the top's is kept and the report names the bottom's as dropped (approximate). KiCad's wire pieces are drawn as strokes; where wire ends meet at a point (four ends with a junction, say), the first stroke runs through it and every other one ends on it, since our crossing wires do not join. KiCad ties a symbol pin to the pad of the same number; the importer resolves that tie once into the binding, so pin mapping stays explicit. Pins of type "not connected" join nothing. KiCad lets one net carry several label names and compares names exactly; ours carry one and compare without case, so names joined by wires take the net's one name (power and global first) and names differing only in case are spelled apart. The importer then checks its own drawing: it works out the source schematic's netlist from KiCad's drawing alone (the connectivity rules above; labels by name in their scope, sheet pins with their sheet's hierarchical labels, power symbols and hidden power inputs by name) and compares it, as groups of the terminals each pin's pad lands, with the imported schematic's nets; a source net the import splits and an imported net that joins source nets are each an import finding (`N3`, refused: an import fault, the pins named in the details), and the summary counts the imported nets equal to the source's. A generated part's power port goes on its pin only once KiCad's wiring is drawn and joined at its pins' KiCad points, as does every hidden power input's port, since a port drawn over a wire end still free would join it. The summary then compares the schematic's nets with the board's, net for net (equal, split, joined with another). Where they disagree the schematic wins, and each disagreement is kept in the project (`schematic.set_net_disagreements`) as a finding while the schematic still disagrees: a board net whose terminals the schematic keeps apart ("joined on the imported board") and a schematic net whose terminals the board has on several nets or on none ("split on the imported board"); waiving one keeps the schematic's net. A footprint without a symbol, and a board without a schematic, get a local label of the board net's name on each pin instead. Zones become fills per copper layer (net, outline, priority, clearance, least width, pad connection, thermal gap and spoke width, island removal) and rule areas, footprints' included, keepouts; our engine fills them. A footprint's and a pad's zone overrides (connection, spoke width and angle, relief gap, clearance) become the part's and the pad's fill overrides (`fill.set_pad_override`). A round pad that states no spoke angle gets its spokes at 45°, as KiCad's plots show for the omitted token; other shapes keep 0° and 90° (this default was approved by the founder on 15 November 2026). Track pieces shorter than the engine's least track length (0.01 mm) are removed and the ends they joined meet at one point (a via's centre when one is there), so nothing dangles; the report counts them. A footprint without electrical pads (a fiducial, a mounting hole) becomes a part without terminals, and one KiCad marks "not in schematic" a board-only part (`component.place_board_only`). A part KiCad marks do-not-populate (the footprint's `attr` flag `dnp`, or the symbol's `(dnp yes)`), or whose value is or carries a not-fitted marker ("DNP", "DNF", "10k DNP"; `crates/kicad/src/population.rs` lists them), is not populated in the default (`variant.set_population`) and keeps its body, since a variant may fit it; the marker leaves the value, and the report names each part (`P7`). Exclude-from-BOM (`exclude_from_bom`, `(in_bom no)`) marks test points, mechanical items and logos, not parts left off: it leaves the population alone, and on a footprint without a model it still means no body, as `exclude_from_pos_files` does. KiCad's public file-format documentation does not describe design variants, so variant data in the files is reported, not imported. The project file's rules become the project's own rule set, marked "From the KiCad project" (`rules.set_project_source`), over the fab profile, which keeps the fab limits: the default class's clearance, track width and via size and the board minimums (copper, edge, hole and hole-to-hole clearances, least track width, annular ring, drill and text height) as overrides, except limits looser than the profile's, which stay out and are counted ("N KiCad rules looser than the fab profile were not taken" in the import report); every other class as a net class (clearance, track width, via size, differential-pair width and gap) with its plain-wildcard name patterns (`*` and `?`, every other character itself, so `+5*` matches `+5V`; a pattern that is a regular expression or names no imported class is named in the report with its reason), and nets assigned explicitly where KiCad assigns them or where our net names would not match the pattern. They are set after the tracks and vias go in (which the file has as they are) and before the fills. Each board then lists the board checks' findings, counted by code. Each layer prints our-only and KiCad-only areas. KiCad's plots come from the installed `kicad-cli`, run on a copy in the ignored `target/kicad-compare/<run>/`, which is deleted after each plot; no tool runs in the design folder, and the design is never written. The summary prints counts, areas and widths only; names and locations stay in each board's local `report.json`. Pieces on round custom-pad primitives, and on the round joins of grown or shrunk custom-pad openings, that KiCad draws as chords may be 6 µm wide (its default maximum error and 1 µm). Mask and paste openings are true offsets in both tools: a grown sharp corner is rounded by the growth. `cargo test -p sparksmith-kicad --test oracle -- --ignored` with `SPARKSMITH_KICAD_ORACLE=1` runs the same comparison on Rust-built synthetic boards; CI runs the synthetic tests without KiCad.

The shared desktop/CLI import gives footprints Sparksmith's own parametric 3D bodies. It never uses a vendor STEP file as a part's body: Sparksmith shows its own photorealistic recreations (generator and part-file models with our materials and markings). A vendor model a footprint references is looked up inside the project folder only (`${KIPRJMOD}`, a relative path, then an unambiguous case-insensitive basename, including ZIP members) and, when found, recorded in the import report's details as a reference source (its project-relative path and SHA-256) for a later recreation; its bytes are not inspected or packed. KiCad library references (`${KICAD*_3DMODEL_DIR}`, `${KISYS3DMOD}`, installation paths) are never resolved. An already-open directory capability confines every filesystem access to the project, including when a path is replaced during import. Symlinks are skipped; ZIP contents stay in memory and unsafe paths are refused. Searches stop at 20,000 directory/archive entries and eight folder levels, with at most 4,096 entries per ZIP, 32 MiB per STEP, 64 MiB per ZIP and 128 MiB of cumulative file reads and decompressed bytes. The total declared uncompressed ZIP content is also capped at 128 MiB.

A footprint that is no part to draw gets no body (`PackageModel::NoBody`, reported as "no body (as in the source)"), as KiCad's own 3D view draws none: it names no 3D model, and nothing is assembled there (KiCad's board-only, exclude-from-position-files or exclude-from-BOM attribute), or it is a net tie, or none of its pads is on a net on a board that has nets (a fiducial, a logo), or it is one surface pad (a test or contact pad) (`sparksmith_kicad::models::no_body`). Every other footprint becomes a real part of the project, made the way a part from the palette or the AI is (one part pathway, founder 19 November 2026): when its lands identify a shipped generator preset's *package*, the preset's generator makes the part through `library.generate` (`crates/automation/src/kicad_models/parts.rs`) with the footprint's own lands as its `land_pattern` ([generator plugins](generator-plugins.md)), in the package frame the fit found, so the generated footprint's copper is the source's pad for pad (checked pad by pad before the part is kept) and the part is placed where the footprint is, the fit's quarter turn and offset composed with the KiCad placement. Its body, symbol (the family's generic one), fields, marking and lead contacts are the generator's, exactly as from the palette; copies of one footprint, and footprints of one package whose lands are equal, share the part. KiCad's symbol pins connect through the pad of the pin's number and the binding's explicit map, never by name; a source symbol's units the part's one symbol has no unit for are counted, their wiring joined to its terminals. Lands are the designer's choice; the package is what identifies the generator. Matching compares *lands* (`crates/automation/src/kicad_models/lands.rs`): a land's number is read without a sub-pad suffix (`41_3` is land `41`, `EP_1` is `EP`) or leading zeros (`01` is `1`); a plated hole smaller than the surface lands of its base number and inside their bounds is a thermal via and left out (paste-only pads are already paste windows); and a round surface land with a concentric non-plated hole is one land round that hole. Lands pair by number or name. A number whose lands differ in count on the two sides (an exposed pad split into nine, against one pad or a four-pad array) compares as one land, the bounds of its pads. Lands whose numbers or names the other side lacks (mounting tabs `S1` against `MP1`, tabs numbered on after the contacts, unnumbered alignment holes, a two-terminal part's `P` and `N`) pair by position as a class, the same count on both sides, as long as no number is left unpaired on both sides (numbering fixes pin 1). In that class a tab may be surface copper or a mechanical land, and an alignment hole plated or not (its diameter within 50%). Polar names (`+`/`-`, `P`/`N`, `A`/`K`) pair with the preset's polar terminals where it declares them (pin 1 is `+` or the anode), which turns the body; otherwise position alone decides. A plated round pad stands for a preset's land round a non-plated hole (a standoff's) when its outer and hole diameters are each within 10%, but only when the footprint's name names the preset, since a plated mounting hole has the same lands. Every pairing other than by equal labels is written into the instance's report entry. Paired lands need the same copper kind, side and holes (round or slot, plated or not, sizes within 50%), and, for surface pads, the same shape class (rectangular, rounded-rectangular and custom lands, compared by their extent, share one; round and oval lands do not; through-hole land shapes are free, since a square pin 1 is a convention). After a common translation and a quarter turn: every land centre lies within the larger of 0.15 mm and 15% of the preset's smallest centre-to-centre distance (its pitch, or a two-pad part's span) of the preset's; the lands' overall extent along each axis is within 25% of the preset's (it tells an 0603 chip from an 0805 one whatever their spans); each land dimension is within 50% of the preset's; and land orientation is within 0.1°. A fitting preset any of whose lead contacts misses the lands of its number (read as above) by the board check's lead-on-land rule is refused. Among the fitting presets, those the footprint's name names come first: a preset's key or alias (generator data), compared as letters and digits only, with at least four of them and one digit, that does not run on into another digit (`1X1` is not in `1X10`); the longest such name wins. Otherwise the presets whose generator declares the longest reference prefix that begins the designator's are preferred (`RFB` is a resistor's `R`, `FB` a ferrite bead's). Two-pad lands do not tell a chip resistor from a capacitor, an inductor, an LED or a diode, and a wrong part is worse than none, so two-pad lands that fit only presets neither named nor of the designator's prefix (an inductor on a chip resistor's lands) make no generated part; multi-pad packages (SOT, SO, QFN and the like) keep their body whatever the designator. Among the remaining presets the one with the smallest largest-centre-error is chosen. Presets within 1 µm of each other (identical lands, as electrolytic size codes have) are told apart by the footprint's fabrication-layer outline against each preset's body (else its courtyard against the preset's courtyard): one within 15% along each axis, with every other at least 2% further off. Anything else is a tie, reported as one, that makes no generated part. The tolerances are named constants in `crates/automation/src/kicad_models/presets.rs`; no package-specific table is compiled into the host. Each source pad lands the package terminal of the preset land it paired with (a thermal via its land number's, holes, mechanical pads and fiducials none). The generator is refused for a footprint, which then becomes a project part of its lands, when a pad lands no terminal of the preset, when one of the part's terminals would join pads a placed copy keeps on different nets, when a land is beyond what a land pattern carries (pad-owned vias, a partly rounded rectangle, an item over 1024 characters), when the generator refuses the land pattern, or when the generated lands differ from the source's; the reason is in the detail. A part number that names another package than the lands are (another preset's name or alias at its start, standing apart), or that runs the matched preset's name on into a variant (`…-1U` for a `…-1` preset), is a finding naming both (`P3`); the lands stay as the source has them. Preset outputs and matches are cached for the import. A shared 300-second cooperative deadline is checked around model lookup and preset work; expiry or generator failure refuses the new import atomically. Individual filesystem and native CAD calls cannot currently be interrupted, so this is not a hard wall-time guarantee. Generator modules and part files are embedded for offline reopening, and every generated part passes the check on load.

A footprint no generator makes becomes a project part of its lands: the same kind of part as an authored one (component, symbol, package, footprint and binding, project-only), its footprint the source's lands, its symbol the KiCad symbol's (else a block of its terminals), named by its part number, else its footprint's name and value, and its package the default model any part without a body has, until a generator's body (`library.make_body`) or a recreation from its datasheet replaces it. The report counts footprint instances made as generated parts (`P1`) and as project parts of their lands (`P2`); each of the latter is also counted, and named in its detail, under one reason: `hidden` (every model reference hidden), `vendor_reference_found` (needs recreation; the vendor file was found and recorded), `vendor_reference_missing` (needs recreation; the referenced file is not in the project or could not be read), `prefix_mismatch` (needs recreation; a two-pad preset fits the lands but its prefix differs from the designator's, the detail names the nearest), `no_lands` (no numbered lands to match), `generator_refused` (the lands are a preset's package, but its generator cannot take them, the detail says why), `kicad_library_reference_no_preset` and `no_reference_no_preset`. The detail's text names the nearest preset and how far its centres were off, or why none applied.

`import-kicad … NEW_FILE.sparksmith` requires both the project and its adjacent import report to be new files. Both are staged before publication and each uses the same create-only primitive. They are published independently: a competing creator claiming the second destination can leave the first newly created file in place while the command reports refusal.

## Footprint wasm proof

To execute the footprint evaluator's golden-hash tests (native/wasm agreement) as WebAssembly under Node (rather than only compile wasm), install Node and the test runner matching the locked `wasm-bindgen` version:

```sh
cargo install wasm-bindgen-cli --version 0.2.129 --locked
cargo xtask wasm-footprint
```

Run these inside `nix develop` when using the Nix toolchain. The runner must be on `PATH`, or set `CARGO_TARGET_WASM32_UNKNOWN_UNKNOWN_RUNNER` to its executable path. This optional runtime check is separate from `cargo xtask ci`; it does not exercise browser UI.

## Offline help

Run `cargo xtask help --update` to regenerate the registry files and the glossary. Run `cargo xtask help --check` to verify them against the current app and catalog. Regeneration preserves the first shipped app version of each existing id. Newly added ids start at the current workspace version. Authored pages live in `library/help/topics`. When a fact in a topic’s `covers` list changes, review the topic against that fact and run `cargo xtask help --stamp <topic-id>`.

`cargo xtask help --site <out>` builds a local manual in `<out>/docs/<app-version>/` and `<out>/docs/latest/`. The search and internal links work offline. Release publication is a separate founder-approved step.

English entries are assembled from the generated facts, English topics and shared workflow methods. Translation files go under `library/help/<locale>/`, for example `de/guide/first-board.json`. Each contains the topic’s `id`, `english_digest` and `text` map returned by `sparksmith_io::help::locale::translation_source`. A translator changes only the map’s text values. The loader preserves references, units, measurements, shortcuts, examples and citations. A missing translation displays the English page. A changed English source displays the English page and marks the translation stale. English is the only language shipped before the first release.

Regenerate the Help and Keyboard shortcuts screenshots for each release using the [macOS VM capture checklist](../tools/launch/README.md#release-checklist-for-help-screenshots).
