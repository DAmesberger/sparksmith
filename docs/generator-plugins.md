# Generator plugins in the project (GP1, GP2)

Design note and contract, 13 November 2026 (GP2: 14 November 2026). GP0 built the module ABI, the SDK, the wasmi host and the `chip` module ([generators/README.md](../generators/README.md)). GP1 makes a part from a module through the one command engine, keeps the module in the project, and checks the part against it whenever the project is opened. GP2 gives every generated part its 3D model: one of the generator's own `.solidcraft` part files, shipped in the generator's bundle, at values the module computes, evaluated through the existing part-file path (one mechanism per job, no model script). Since slice D1 (15 November 2026) the desktop's catalog search, generator gallery, Place palette and part editor make parts only through the shipped generators.

## Decisions

| # | Decision | Why |
|---|---|---|
| G1 | **Identity** (slice B4, 14 November 2026). A part's key is the generator's **id** (its description's `id`) with the **params hash**, the SHA-256 of the canonical request (`{abi, scope, params}`, complete, as recorded). The generator's **version** tells revisions of that lineage apart. The **result hash** is the SHA-256 of the canonical generation, the integrity check. The **module hash** names the embedded bytes the check on open runs; the **bundle hash** (the manifest's, which names the module and part files) is provenance and what a person approves. Before B4 the key was the module hash with the params hash, so it depended on the build host. | Complete parameters are filled from the module's description before hashing (`sparksmith_generator_abi::params::complete`, the one completion the core and the host both call; tests compare implicit and explicit defaults and the core's and host's bytes over every shipped default and preset), so a default changing in a later module can never change a part's key. The scope is in the request, so a component and a package from the same values have different keys. |
| G2 | **Provenance beside the revisions.** `Library::generated` lists one `GeneratedPart { root, expansion, from }` per part: the root (the component, or the package of a package-scope part), every revision the expansion made, and `GeneratedFrom { generator, version, module, bundle?, abi, scope, params, result, ids }` (`ids`: the key-to-id map, G4). It is not a field of the revision bodies. | Like origins: drafting a generated revision and publishing it again makes the person's own part, which claims nothing. A body field would be copied by `library.draft_from` into a revision that is no longer what the module makes. |
| G3 | **Embedding.** The module's bytes are a packed asset of media type `application/wasm`, one container entry per hash (`assets/sha256/<hash>`), so every part one module made shares one copy, and parts of two module versions keep both. The asset store's clean-up treats a module a record names as in use. | The container already stores assets by hash with offline reopen, bounds and refusal of unknown or mismatched entries ([container](component-model.md)). No new entry kind or format version. |
| G4 | **Expansion** (keys: slice B1). `library::generated::expand` maps a generation to definitions, a pure function of the generation, the five lineage references and the part's key-to-id map (`expand::KeyIds`, one map per definition: `t:`/`f:` terminals and their functions, `u:`/`g:UNIT/KEY` units and drawings, `t:` package terminals, `p:`/`g:` pads and drawings, `courtyard`). A key the map holds keeps its id; a new key takes the next id after every id the map has held; the map never forgets a key. A new part's ids follow the generation's order (terminals 1…n with their fixed functions n+1…2n; units each followed by their graphics; package terminals; pads, then silkscreen, assembly and courtyard drawings). Making a part again starts from the replaced part's map, so a module that inserts a pad leaves every other pad's id, and the tracks on it, as they were (`regenerating_with_an_inserted_pad_keeps_every_other_id_and_the_tracks`). The check on open expands with the recorded map and refuses a generation with keys the map does not name. | The same function rebuilds a stored part for the check on load, so a part is either exactly what its module makes or refused. |
| G5 | **The core never runs a module.** `library.generate` uses the engine's host runtime (`Engine::set_generators`, a `GeneratorRuntime` from the ABI crate). The session sets a worker runtime; a host without one refuses `library.generate` (`generator.runtime`). The load check lives in `sparksmith-io`, which runs the modules through `sparksmith-generators` (moved to layer 1 beside the core; it depends on the ABI only). | The core stays file-free and wasm-compatible, and every open path (desktop, session, recovery) goes through `sparksmith_io::read_project`. |
| G6 | **Off the caller's thread.** `sparksmith_generators::worker::Worker` runs calls under the host's fuel, memory and decode limits, waits at most a wall time (2 s, the README's target) and watches a cancel flag. At most four workers may be active across the process; a further interactive call is refused as `generator.busy` before its inputs are copied or a thread is created. Batch work nobody is there to retry (a KiCad import making its parts' models, `session::generators::batch_runtime`) is admitted with `Worker::waiting_until`: it waits for a worker up to its deadline, still watching the cancel flag, and only then is refused as busy; its wall time starts once admitted. A headless session's calls (the CLI's scripts and replays, MCP and JSON-lines callers, the built-in agent's headless runs, tests' sessions) come one after another with nobody to retry, so the runtime a session installs when its engine has none (`session::generators::session_runtime`) uses `Worker::waiting_for`: each call waits up to 60 s for a worker. The desktop's own runtime keeps the immediate refusal, so its UI thread never waits. A timed-out or cancelled call is refused (`generator.timed_out`, `generator.cancelled`), but its thread keeps its permit through execution, decoding and cleanup, then drops its unused result. | wasmi fuel does not cover host decoding. The worker bounds the caller's wait, while structural decode budgets and retained permits bound abandoned work. |
| G7 | **Context parameters.** A parameter the request leaves out whose description names a project setting is filled from the project: `project.land.chip_gap_min`, `project.land.gull_wing_width_extra` and `project.land.exposed_pad_clearance` (the land rules), `project.mask.web_min` and `project.mask.expansion` (the mask rules) and `project.symbols.resistor_style` (the symbol conventions). Every other is the module's default. Then the parameters are frozen into the record. | The module never reads project state; the part key records what was used. |
| G8 | **Shipped modules are committed builds**, one hash each: the SHA-256 of `library/generators/<name>/<name>.wasm`, which the bundle's manifest records (no lock file since 14 November 2026). `cargo xtask generators build --ship` writes each generator's bundle there (G10); `check` (in CI) fails when a clean build of the source differs from the committed module (not compared on Windows), a bundle file differs from what the crate builds, or a file there belongs to no generator. | The build is reproducible across checkout paths and hosts (macOS aarch64 and Linux x86_64 measured; `generators/README.md`, "Reproducibility"), so the committed module proves on every host that it is what the source builds. A part key does not depend on the bytes (G1), and every platform ships the one committed copy. |

## The 3D model (GP2)

| # | Decision | Why |
|---|---|---|
| G9 | **The model is a part file with values.** A generation's `model` is `PartFile { asset, values }`: a part file of the generator's bundle by SHA-256 and integer values for its parameters (nanometres, millidegrees, counts, by the parameter's unit). The module never runs Solidcraft; the file holds the geometry, the module the logic (which file, which values). | Solidcraft's own parametric designs, authored in Solidcraft, are the one 3D mechanism for every part, generated or not; no Sparksmith geometry language and no second stored model kind. |
| G10 | **The generator bundle.** `library/generators/<name>/` holds `generator.json` (format, name, the module and each part file by path and SHA-256, with each file's title, licence and provenance), `<name>.wasm` and `parts/`. Its identity is the SHA-256 of the manifest's bytes. `cargo xtask generators build --ship` writes it from the crate (`generators/<name>/parts/` with sidecars), `check` verifies it, `sparksmith_io::generator_bundle` reads it and refuses a missing or changed file by name. | One hash approves the module and every file it may name; the module names files by hash (`build.rs`), so the result hash covers which file the part uses. |
| G11 | **The host evaluates, the core stores.** `library.generate_part` asks the engine for the complete request (`commands::generator_request`), runs the module, finds the part file (the bundle, or a Model the project packs), evaluates it at the values (`part_file::evaluate`) and refuses unless (a) no finding blocks, (b) its bounds lie within 10 µm of the generation's envelope (centred: the smallest centred box holding them, so a part with unequal sides reaches it on one side only), and (c) every lead contact lies under a body of a lead material. `library.generate` takes the result (`Generate.model`: the Model definition, bytes when not packed, the values in the file's units and the derived data), checks that it is the file and the values the module names, and stores the file as a Model of format `solidcraft` (the newest one packing those bytes, or a new lineage published with the part) and the package as `PackageModel::PartFile`. | The core never evaluates a part file; it can still check that the host evaluated the right one. Two parts of one generator share one packed part file. |
| G12 | **The check on load** compares the stored package's model with the generation (the Model packs the named bytes, the values are the module's) and then the stored revisions with the expansion, the package holding its stored model. The derived data (bounds, surfaces) is the stored evaluation, rechecked by every board build (`part_file.stale`), not part of the equality. | Reopening needs no Solidcraft evaluation; a changed value or file is still refused. |
| G13 | **A model is required.** The host refuses a generation without one (`generator.invalid_model`), the core a `library.generate` without the host's evaluation (`generated.model_unevaluated`). A part that is complete as its lands says so explicitly with `Model::NoBody` (a fiducial: the board draws its land, 21 November 2026): nothing is evaluated, and the package's model is `no_body`. | A part must never exist without its 3D model (founder, 14 November 2026). |
| G14 | **Generator version.** `Description.version` (u32, from 1) is the generator's version within its `id`; a higher version is newer, and it is recorded with each part (B4). The chip module is version 2 (15 November 2026: an LED's pin-1 dot). | What "a newer version of the same generator" means when a part is regenerated. |

**Markings as generator data** (19 November 2026). A generation's `marking` is the part's default marking, made by the generator's own rule from its parameters and filled per placed part by the host from the part's fields; no generator writes per-part text. Where a manufacturer Part is fitted (the instance's own, or an assembly variant's substitute), its rated values are the part's data and win over the instance's field values, which are requirements: a ±1 % Part prints its ±1 % code even where the instance asks only ±5 % or names no tolerance (20 November 2026). Lines are text templates (`{mpn}`, `{field:<standard field>|<format>}`), and a placeholder may list alternatives separated by `;`, each with a condition on a field's number after `?`: the first that holds and renders is drawn, and nothing is drawn when none does (a wrong code is never drawn). Formats are the IEC 60062 codes `code3`, `code4`, EIA-96 `eia96`, the capacitor code `cap3`, voltage letters, and `num:<SI prefix>` (the number without its unit). A marking may be printed in a colour (`colour`), placed on a named marking surface of the part file (`surface`, a plane or a cylinder) and round a cylinder (`wrap`), carry a polarity mark, SVG artwork (the host packs it under the generator's licence) and further markings on other surfaces (`decals`). The rules shipped:

- **Chip resistors** (`chip`, `resistor_code`): by size (`auto`) none on 0402 and smaller, three digits up to 0603 (`103`, `4R7`, `0` for a jumper), four digits on larger chips where the part's tolerance is 1 % or better (`1002`), else three digits; a preset may choose EIA-96 at 1 % (`01C`; the 0603 preset does, as Yageo's RC_L data sheet marks 1 % 0603 chips: E-96 values and the E-24 values 10, 11, 13, 15, 20 and 75 in EIA-96, so RC0603FR-0710KL prints `01C` and RC0603FR-07806RL `88A`, other E-24 values in three digits). The tolerance is the fitted Part's rated tolerance (the part number's tolerance letter, F for ±1 % on Yageo, entered as the Part's Tolerance), else the instance's. A value no code holds exactly draws nothing. The code is white ink on the overcoat. Not drawn yet: the short bar Yageo prints under the middle digit of a 1 % E-24 value on 0603 (`471` with a bar for RC0603FR-07470RL).
- **Chip LEDs**: a green bar at the cathode end (pin 1, −x) on the lens top.
- **ICs and diodes** (`gull-wing`, `tabbed`, `no-lead`, `molded`): the presets mark `{mpn}`, the placed part's manufacturer part number, laser-etched (with the pin-1 dot where the moulding has no pin-1 feature); a part without one shows only its pin-1 dot. A diode's cathode band is the band body of the `-band` part files.
- **Top-mark codes** (`{code}`, 20 November 2026): where a manufacturer marks a small package with a code instead of its part number, the preset carries the manufacturer's marking table (`marking_codes`, `MPN=CODE` per orderable part number, from the datasheet's package option addendum) and marks `{code}`: each placed part shows the code of its own part number (compared in upper case, spaces ignored), and a part number the table does not list shows no code, never another variant's. The table travels with the generation (`Marking.codes`) and is stored with the marking (`MarkingSpec::codes`). The no-lead generator's TI DML0010A and RXB0014A presets use it.
- **Aluminium electrolytics** (`electrolytic`): the capacitance in µF and the rated voltage (`100` over `16V`) in black on the bare part of the can top beside the inlaid negative sector; the vent cross is the `-vent` part file's score, a fine V-groove 0.12 mm open and 0.015 mm deep (est.) whose shallow walls show a subtle cross from any side. A radial polarised capacitor (`tht`) prints its values in pale ink round the sleeve opposite the negative lead and the negative stripe with open minus signs (SVG artwork, `sparksmith_generator_sdk::marking::stripe_svg`) facing it, on the part file's `marking-sleeve` cylinder. Both families select Capacitance, Rated voltage and Tolerance, so each placed part holds its own values.
- **Moulded tantalum capacitors** (`molded` 5, `value_code`): a polarised capacitor prints the capacitance in pF as three digits and the rated voltage's letter on one line beside the anode band (`106 C`: 10 µF, 16 V), as the Kyocera AVX TAJ data sheet marks every case A to E (TDS-PTNO-0024 Rev 3, Marking; the maker's logo and ID code line are left out). The letters are the standards' `tantalum` table (Vishay 293D, TDK B45196E and AVX TAJ agree). The band is the `-band` part file's body at terminal 1, the anode. A voltage with no letter, or a capacitance no code holds, draws no line. The presets give the text height (est. from the case size); `value_code` `none` leaves the part unmarked. The generic family `tantalum` (`tantalum B 10u 16V`, `tantalum case A`, `tantalum 7343-31`) selects Capacitance, Rated voltage and Tolerance.
- **Module shield labels** (`module` 7): the presets' label parameters (`label_name`, `label_logo`, `label_ce`, `label_mic` with `label_mic_id`, `label_fcc_id`, `label_ic_id`, `label_cmiit_id`, `label_company`, `label_status`, `label_matrix`) fill the generator's label template (`generators/module/marking/shield-label.svg`; a line naming a value the preset leaves empty is left out), laser-etched into the whole can top (`Marking.metal`, `marking-can-top`). The template is laid out as Espressif's laser-marking artwork for the ESP32-S3-WROOM-1U (its FCC 'Label' exhibit, 15.65 × 17.50 mm, with the MIC row of PCN20230802): the logo, the module name (medium weight), the CE and Japanese conformity marks with R and the MIC number, the FCC ID, IC and CMIIT ID lines, the maker's name in Chinese, the specification identifier (`label_status` and `{code}` from `marking_codes`: `ESP32-S3-WROOM-1U-N16R8` prints `XXN16R8`) and a Data Matrix of the placed part's `datamatrix` variable (a sample of the code's 18 characters while none is set). Marks and the Chinese name are installed library artwork named by id (see below). The ESP32-S3-WROOM-1, -1U and ESP32-S31-WROOM-3 presets carry labels; their sources are in each preset's note.

**Artwork templates** (20 November 2026). Marking artwork (a generator's `Marking.artwork`, or SVG packed with `library.pack_artwork`) is drawn per placed part:

- In `text` and `tspan` content each `{…}` placeholder of the text templates becomes its value for the part (`{mpn}`, `{code}`, `{field:…|code3}`; a generator writes standard field names, which the host makes the project's as in lines), or nothing when it has none: never another part's text, never the placeholder. `{{` and `}}` are literal braces.
- An element with `data-if="<condition>"` is drawn only when its condition holds, with everything in it, so groups are shown, hidden or swapped by the part. Conditions are the templates': a field's number (`field:D8<=1%`), a text the part gives compared as part numbers are (`mpn=…`, `^=` starts with, `$=` ends with, `*=` contains; also `code`, `manufacturer`, `field:<lineage>`, `var:<name>`), a name alone (it has a value), and `!` negating. Text placeholders may use the same conditions in their alternatives (`{code?mpn^=ESP32-S3;mpn}`). A condition on a field in a generator's artwork names the field by lineage, as only text placeholders are rewritten.
- `<use data-art="<id>" x y width height/>` draws the installed library artwork `<id>` fitted into the box (centred, aspect kept) in the marking's finish. Installed artwork is optional data, read at startup from the shipped library's `artwork/<id>.svg` (ids `a-z`, `0-9`, `-`); one that is not installed is left out quietly and the rest is drawn. Makers' marks and certification marks are not in this repository: they belong to their owners and are installed with the parts library that uses them.
- `<use data-code="datamatrix" data-payload="<template>" x y width height/>` draws the generated 2D code of the payload (its placeholders bound as text's are) as a square centred in the box, in the marking's finish: a Data Matrix ECC 200 (`datamatrix`, the smallest square symbol that holds it) or a QR Code (`qr`). An empty payload, or one the code cannot hold, draws nothing.
- Text may be heavier: `font-weight` (`bold`, or 1–1000) above 400 grows the built-in font's glyphs by an outline offset (round corners; 0.03 em a side at 700, est.), as the font has one face. Each run of glyphs apart along a line is filled on its own, which keeps a label's text within the decal's triangle budget.
- A root `data-fit="view-box"` fits the artwork into its box by its view box rather than by what it paints, so a label keeps its frame whichever groups the part shows.

The core binds a template for each placed part (`marking::bind_artwork`, `artwork::bindings`): the layout's `LaidElement::Artwork` carries `bound`, each placeholder's text and each condition's result, and the drawing side (`sparksmith_solidcraft::marking::template::apply`) puts them in before the SVG is painted. Decals are tessellated vector outlines, crisp at any zoom, made on the model worker with the board; the decal cache is keyed by the layout, `bound` included, so two parts of the same variant share one decal and a changed part number rebuilds only its own. The live PCB 3D view, the look pictures and the Component 3D preview draw through this one path; markings are display only and are not exported.
- **Text height** (`marking_height`, `Marking.text_height`, the spec's `text_height_nm`): the capital height each preset gives, as the part carries its print; a line too long for the marking area at it is set smaller (never below the minimum legible height), and 0 fits the text to the area (at most 1.2 mm). The preset values are estimates from manufacturers' product photographs and marking drawings, read for size only: chip resistor codes 0.4 mm on 0603, 0.5 mm on 0805, 0.65 mm on 1206 and 1210, 0.9–1 mm on 2010 and 2512; SOT-23 0.45 mm, SC-70 0.35 mm, SOT-89 0.55 mm, SOT-223 0.7 mm; SOD-123 0.45 mm, SMA 0.75 mm, SMB 0.85 mm, SMC 1 mm; SOIC 0.65 mm (0.9 mm wide body), SSOP 0.6 mm, QSOP 0.55 mm, TSSOP 0.5–0.6 mm, MSOP 0.4 mm, QFP 0.7–1 mm by body size; DFN and QFN 0.35–0.65 mm by body size; SMD electrolytic can tops 0.7–1.3 mm by can diameter (0.9 mm on 6.3 mm); radial sleeves 1–1.8 mm by diameter.

**The chip part files.** `generators/chip/parts/` holds `chip-resistor`, `chip-capacitor`, `chip-ferrite` (inductors and ferrite beads) and `chip-led`, authored at a 0603 chip (`crates/solidcraft-integration/tests/author_parts.rs`, `author_chip`), parameters `length`, `width`, `height`, `termination`, `body_round`, `end_round`, plus `overcoat` (resistor) and `substrate`, `lens_round` (LED): end caps of matte tin that are the part's outline and stand proud of the body, a resistor's dark overcoat inset from its edges and short of the caps, an MLCC's bare ceramic, an LED's die under its clear lens, and a `marking-top` plane. Each passes the part-file check (finding: the cold evaluation over 100 ms on a loaded machine).

**Refusals** (word for word in `crates/generators/tests/refusals.rs`, `missing_or_malformed_models_are_refused_in_plain_words`): no model; a part file named by something other than a SHA-256; a value beyond 1 m, not a whole number, or under a name no part parameter can have. Each ends "Nothing was changed." The core refuses a missing evaluation, another file than the module names, and other values (`library/generated/tests.rs`); the session refuses a file in neither the bundle nor the project, a blocking finding, bounds off the envelope and a lead contact under no lead body.

**The header part file** (phase C, 14 November 2026). `generators/header/parts/pin-header.solidcraft` is parametric in its counts (parameters `rows`, `pins`, `pitch`, `row_pitch`, `body_height`, `pin_side`, `pin_above`, `pin_below`, `corner_round`, `edge_round`): the posts are a body pattern, the base's holes a feature pattern of one cut. Its posts reach below the seating plane, which the part-file check and the generated-part envelope check allow for leads (`part_file::seated_bottom`). Provenance: the former in-code header builder's construction, made parametric ([parity](#parity-at-retirement)).

**The gull-wing part files** (phase C, 15 November 2026). `generators/gull-wing/parts/gull-wing-two-sided.solidcraft` and `gull-wing-four-sided.solidcraft` are parametric in their counts (parameters `leads`, `leads_short` (four sides), `pitch`, `body_length`, `body_width`, `body_height`, `standoff`, `span`, `span_x` (four sides), `lead_width`, `lead_thickness`, `foot_length`; the lead profile's bends, the rounds and the pin-1 dimple are derived parameters of the file). Each lead row is a body pattern of one formed lead drawn from expressions, the body's root cut a feature pattern of one cut. The module fills its land width from `project.land.gull_wing_width_extra`. Provenance: the former in-code gull-wing builder's construction, made parametric ([parity](#parity-at-retirement)).

**The no-lead part files** (phase C, 14 November 2026). `generators/no-lead/parts/` holds `dfn`, `dfn-ep`, `qfn` and `qfn-ep`, parametric in their counts (parameters `terminals`, `terminals_short` on four sides, `pitch`, `body_length`, `body_width`, `body_height`, `terminal_length`, `terminal_width`, `frame`, `edge_round`, `mark_radius`, `mark_depth`, `pad_length` and `pad_width` with a pad). Each side's terminals are a body pattern, the body's pockets for them a feature pattern of one cut; the module picks the file by sides and exposed pad, since no parameter can remove a body. Provenance: the former in-code no-lead builder's construction, made parametric ([parity](#parity-at-retirement)).

**The molded part files** (phase C, 14 November 2026). `generators/molded/parts/` holds one file per terminal form, each with and without the polarity band (a band is a body of its own, so the module picks the file): `molded-flat`, `molded-bent`, `molded-j-lead` (an epoxy body, two tin leads, parameters `body_length`, `body_width`, `body_height`, `span`, `terminal_length`, `terminal_width`, `lead_thickness`, `lead_root`, `corner_round`, `edge_round` and per form `lead_length`, or `lead_exit`, `lead_shoulder`, `body_bottom`, `bend_1`, `bend_2`) and `melf` (glass between tin caps: `body_length`, `body_diameter`, `span`, `terminal_length`, `cap_diameter`, `cap_round`), plus the `-band` variants. Bent leads are three mitred boxes whose bend edges are rounded about the bend centre (outside `bend + thickness / 2`, inside `bend − thickness / 2`), J-leads a box with the inside cut out, MELF bodies circles on YZ sketches at expression-placed centres. The band's size and `marking-top` (the form's marking area) are expressions over the body, so the module does not set them. A part file's own material is kept where the package chooses none (a MELF's glass), and the marking materials read as role `marking` (`part_file::role_of`). Provenance: the former in-code molded builder's construction, made parametric ([parity](#parity-at-retirement)).

**The grid part files** (phase C, 15 November 2026). `generators/grid/parts/` holds `grid-ball` and `grid-land` (full grids) and `grid-ball-voids` and `grid-land-voids` (grids with empty positions), parametric in their counts (parameters `rows`, `columns`, `pitch`, `row_pitch`, `body_length`, `body_width`, `body_height`, `contact_diameter`, `contact_height` (a land's thickness on an LGA), `edge_round`, `mark_radius`, `mark_depth`). The contacts are one seed at A1 and one two-way body pattern of every position; a land grid's body is cut round them by a feature pattern of one cut. **Depopulation is pattern plus cut-outs**: the `-voids` files have 16 rectangular cut-outs (`void_<k>_x`, `_y`, `_length`, `_width`), made before the body exists, so each removes the contacts inside it whole and nothing else (an LGA's body is filled again over them); the module covers the empty positions with rectangles of empty positions (a greedy cover, overlaps allowed) and repeats the first for the slots it does not need, which then remove nothing more. A map that needs more than 16 rectangles (a checkerboard) is refused in plain words. Why not one file per class: a ring, a ring round an island, a channel and a missing corner are all a few rectangles, so one file covers them, where per-class files would multiply with every shape. Why not a pattern that skips instances: the pinned Solidcraft has none (adding one upstream needs the founder's go). Limits: at most 1000 positions (Solidcraft's 1000-instance pattern limit) and 512 contacts (the host's lead bound); looks are kept by body name, so every name the pattern can give (`contact 1 (2)` … `(512)` full, `(1000)` with cut-outs) carries its look, which makes the files 156–321 KiB. Provenance: the former in-code grid builder's construction, made parametric ([parity](#parity-at-retirement)).

**The tabbed part files** (phase C, 14 November 2026). `generators/tabbed/parts/` holds `tabbed-rows` (SOT-23, SC-70), `tabbed-tab-lead` (SOT-223, SOT-89) and `tabbed-flange` (DPAK, D²PAK), the module choosing one by its `tab` parameter. Inputs `pitch`, `body_length`, `body_width`, `body_height`, `standoff`, `span`, `lead_width`, `lead_thickness`, `foot_length`, `row_s_leads`, `row_s_step` (and `row_n_leads`, `row_n_step`; `tab_width`, `tab_length`; `flange_protrusion`), `corner_round`, `edge_round`; the bent lead profile is derived parameters over them (the outline's points and the bend radii as expressions), so the file follows any value without Sparksmith. Each has a `marking-top` plane. Provenance: the former in-code tabbed builder's construction, made parametric ([parity](#parity-at-retirement)).

**The through-hole part files** (phase C, 14 November 2026). `generators/tht/parts/` holds one file per lead topology, over plain parameters: `tht-axial`, `tht-radial` (straight round leads), `tht-radial-formed`, `tht-dip` (each row a body pattern of `per_row` strips, the root cuts a feature pattern), `tht-to` (a pattern of `pins` square leads) and `tht-to-formed` (three leads, the outer two formed). The module picks the file by construction and lead form and gives every input value (`lead_pitch`, `lead_diameter`, `lead_below`, `standoff`, `root`, the body's sizes, `bend_radius`, the rounds); a bend's radius and tangent length are the file's own expressions (`<lead>_r<k>`, `<lead>_t<k>`). The radial files carry the can top as `marking-top`. Provenance: the former in-code through-hole builder's construction, made parametric ([parity](#parity-at-retirement)).

**The module part files** (phase C, 15 November 2026). `generators/module/parts/` holds `module` and `module-diagonal` (LGA pads) and `module-castellated` and `module-castellated-diagonal` (castellated pads): a soldermasked board on its gold pads, a nickel-silver can with rounded top edges and the printed antenna meander, parametric in everything a module form can vary. One file serves every module of its kind because **what a module lacks is parked and cut away**: the file has eight row slots, two a side (`row_<i>_count`, `_x`, `_y`; seed `row <i> pad` and a body pattern along the side), per slot a plated half ring and a cut of the board with its pattern in the castellated files (`notch_<i>_count`, `_x`, `_y`, `notch_radius`, `plating`), a two-way ground array along the axes or turned 45° (`ground_rows`, `ground_columns`, pitches, sizes, the seed at `ground_x`, `ground_y`), sixteen single pads (`single_<k>_x`, `_y`, `_length`, `_width`), a notch cut from the can at its +x +y corner (`can_notch_x`, `_y`, `_width`, `_length`), an antenna connector (`connector_x`, `connector_y`: an insulator base, a round shell and the centre contact) and the meander (a head, `antenna_units` joined copies of one turn and a tail; `antenna_turns`, `antenna_step`, `antenna_depth`). A slot without a row, a missing ground array, antenna, notch or connector and the unused singles are placed at `park_x`, 100 mm beyond the −x edge, and one cut removes everything there, so the bodies left are exactly the module's. The module turns a ground array of any multiple of 45° into the file's directions (swapping counts and moving the seed for quarter turns) and refuses other turns, more than two rows on a side, more than 64 pads a row, 16 ground pads a side or 16 single pads, naming the limit. Why castellated files of their own: each notch is a cut of the board (about 30 ms), so LGA modules evaluate without them. The marking planes are the module form's anchors over the file's parameters (`mark_pcb_depth`, `mark_antenna_depth` give them a size of at least 1 µm). Looks are kept by body name for every name the patterns can give, which makes the files 299–498 KiB. Provenance: the former in-code module builder's construction, made parametric ([parity](#parity-at-retirement)). The ESP32-S31-WROOM-3 part file in `library/parts/` stays library data, as authored; the module generator's preset of the same name builds the same 110 bodies. **The module's own soldermask** (version 5, 20 November 2026): `mask_colour` (green, the default, or black) chooses between the four files and their `-black` twins, whose board and antenna are black soldermask (`solder_mask_black`, `solder_mask_black_over_copper`); an appearance is no parameter, so the colour is a file of its own, as the wire-to-board shrouds' colours are. The module's board keeps its own colour whatever the host board's soldermask setting (`layout.set_fabrication`); the Espressif presets are black, as the modules are made.

**Two optional ABI fields** (module slice, 15 November 2026): `Footprint.keepouts`, copper keep-outs of the host board (a name and a closed polygon, every copper layer: a radio module's antenna clearance), stored as the footprint's `FootprintKeepout`s; and `Pad.number`, the number shown when several pads share one (a module's nine ground pads numbered "95", each with its own key), the key when absent. Both are left out of the canonical JSON when empty, so other generators' output and golden hashes are unchanged; their modules are rebuilt because the SDK's code changed. A generation's lead bodies under no lead contact bind to the terminal of the land they stand on (`session::generated_models`), so every pad of a ground array highlights with its net though the package names one contact per terminal.

**A given land pattern** (19 November 2026). Every generator takes the parameter `land_pattern`: the lands as given, a manufacturer's recommended land pattern or a board's own lands (a KiCad import), one pad per item, each the ABI's `Pad` in canonical JSON in the package frame (the body centred on the origin, as the generator draws it), at most 1024 items of at most 1024 characters. Empty (the default) keeps the generator's own lands. When it is not empty the generation's pads are exactly these: every land names a package terminal of the generator (or none, for a non-plated hole, a mechanical pad or a fiducial), every package terminal has a land, keys are unique and only paste has windows, else the module refuses it in plain words (`param.land_pattern`, no part made). The body, leads, symbol, fields and marking stay the generator's; the courtyard and the silkscreen outline are drawn again round the given lands. The SDK declares the parameter for every generator and applies it around the generator's own `generate` (`sparksmith_generator_sdk::land_pattern`), so a generator neither declares nor reads it; adding it raised every generator's version by one (G15: a part made again with the same parameters becomes the next revision). The ABI's `Pad` carries what a given land needs, each optional and left out of the canonical JSON when absent, so other generations encode as before: `kind` (`mechanical` or `fiducial`, copper that lands no terminal on purpose), a hole's `offset` from the pad centre and a slot's `rot_mdeg`, the `outline` shape (lines and arcs, an arc by its bulge in parts per billion), `windows` paste openings (rectangles, circles, polygons) and an empty `number` (an unnumbered pad).

**A pin table** (22 November 2026). Every generator takes the parameter `pin_table`: the real part's pins from its datasheet's pin table, one `NUMBER=NAME:KIND` entry per pin (at most 1024 entries of at most 128 characters), the number a package terminal of the generation. A generator numbers a package's terminals and leaves them passive, since a package does not say what the chip in it does; the pin table does. Each listed terminal (through the binding) takes the name and the kind's functions: `power_input`, `power_output`, `input`, `output`, `bidirectional` and `passive` are fixed, `open_drain` and `open_source` are outputs whose drive only sinks or only sources (a power-good flag; `Terminal.drive`, mapped to the core's drive, so ERC's drive matrix lets them share a net with a pull-up or each other), and `io`, a GPIO, is an input (the design default) that can be selected as an output, so two GPIOs on one net do not fight; `nc` and `reserved` are pins the datasheet says are not connected or reserved (`Terminal.unconnected`, optional, left out for an electrical terminal), which the host keeps as device NC and reserved terminals: never wired (`schematic.connect` refuses them) and needing no project decision (review §9; the ESP32 module presets' pins 33–39 and 91 and the TI DML0010A and RXB0014A presets' NC pins say `nc`). A terminal not listed keeps the generator's name and kind. A number the package lacks, a number twice, two numbers of one terminal with different names or kinds, or an entry that does not read is refused in plain words (`param.pin_table`, no part made); a package-scope part checks the table and has no terminals to name. The SDK declares it for every generator and applies it around the generator's own `generate` (`sparksmith_generator_sdk::pins`), as it does the land pattern; adding it raised every generator's version by one (G15). Presets of particular parts carry their datasheets' tables as data (the ESP32 module presets from Espressif's pin definitions, the TI, Sensirion and WS2812B presets from theirs, each source in the preset's note), and the datasheet workflow's package plan gives the one it reads, so the generated part a person places before publishing the drafts has the pins' names and kinds; the pinout document then adds functions and rules. The ABI carries the extra functions as `Terminal.alternates` (further directions, each once and none the default's, at most 5), left out when empty; the host expands them into the terminal's functions after the default, which is the design default.

**Orderable part numbers** (22 November 2026). Every generator also takes `part_numbers`: the manufacturer part numbers the part is exactly, one `MANUFACTURER=MPN` per entry (at most 64, each side at most 128 bytes, each part number once), as the maker's ordering information prints them. A complete part returns them as `Generation.orderable` (left out when empty; a package has none), and `library.generate` publishes each the component does not have yet as its manufacturer Part (`<manufacturer> <mpn>`, pinning the new revision and its binding) in the same undo step; a regeneration carries the existing ones. A part made for exactly one part number is fitted with that Part when it is placed (`component.place`, in the same step; `generated::sole_orderable`, left generic when the Part would not agree with the instance), so the BOM names it at once; for several (a module's ordering codes) the person chooses one (Resolve parts or the part card). The ESP32 module presets carry Espressif's ordering codes, the TI and ADI presets theirs (the parts their marking tables list), and the datasheet workflow's plan gives the part it was asked for. The SDK declares and applies it like the pin table (`sparksmith_generator_sdk::orderable`; the crate root's `described` and `generate` chain all three).

**Lead contacts on the package** (19 November 2026). `library.generate` stores the generation's lead contacts on the package (`PackageDefinition::leads`, by the package terminal each names), so the board check finds a generated part's lead off its land. Like the fields, they are host data beside the expansion: the check on load keeps the stored ones, so parts made before packages carried them still open.

Shipped generators capture the board's signed mask expansion per side in `board_mask_expansion_nm`. The footprint stores it as its default for library checks. Inherited pads on the assembled board still follow the active board rule. The no-lead family uses the captured expansion on both sides when sizing estimated lands for the requested web. Silkscreen clipping, pin markers and the SDK's explicit land-pattern replacement use it as well, as far as the opening reaches beyond the pad: beside a shrunk opening or a tented pad, ink keeps its clearance from the copper, which the silkscreen check measures from and the host's own drawing keeps (both drawings are tested on `crates/generator-sdk/src/silk_cases.rs`). A new invocation of an older generator with inherited pads on a board whose expansion differs from the historical footprint default reports `generated.mask_expansion_unsupported`. Offline verification uses the embedded module and the original complete request, including after a profile change.

## Regenerating a part

| # | Decision | Why |
|---|---|---|
| G15 | **Regenerate rule** (founder, 14 November 2026). The same module with the same complete parameters returns the part the project holds; nothing changes. The same generator (`id`) at the same `Description.version` built to other bytes does the same. A **newer version** with the same parameters makes the next revisions of the part's lineages, published and recorded as one undo step; placed instances keep the old revision until the update preview is applied. An **older version** is refused (`generated.older_version`). | "Same parameters" means every recorded parameter has the same value and a parameter the newer module adds was not given (so it takes its default or project setting); otherwise it is another part beside the old one. The part made again is the newest one an earlier version of the generator made from those parameters in the same scope (highest version, then revision). Publishing a revision is a library change that moves nothing placed, so it is one step; moving instances is a design change, so it goes through `project.preview_update` / `project.apply_update`, bound to the project revision with the impact listed (AGENTS.md). |

## Commands

- **`library.generate`** (core, Edit): `{ module: {hash, data?}, scope, params, name?, replaces? }`. Bytes are needed only when the project does not embed the module yet; they must hash to `hash`. The command describes the module, completes the parameters (G7) and applies the regenerate rule (G15): it returns the part the project already holds (`created: false`, the part unchanged), refuses an older version, or generates, expands, publishes the revisions (new lineages, or the next revisions of the replaced part's), embeds the module and records the part, as one undo step. A component-scope part also carries its exact manufacturer Parts: each Part whose latest revision pins an older revision of the component is republished for the part's revision, its binding moved to the revision that component lists for the same binding lineage (as `library.publish_with_parts` does; nothing matched by name), so the update that moves the instances takes it (`Outcome::Generated { report }`: root, revisions, key, result hash, created, `replaced` (the old root, when made again), the module's notes). `replaces` names the part to make again explicitly; an older version is refused there too. Any refusal leaves the document unchanged.
- **`library.generate_part`** (session, Edit): `{ generator | module, scope, preset?, params, name?, expected_revision }`. Reads a shipped module by name (`ShippedLibrary::generator`, bounded at 1 MiB) or an embedded one by hash, merges a preset's values under `params`, and applies `library.generate`. When the part was made again over a component the project places, the reply adds `update`: the `project.preview_update` plan (`ComponentRevision` of every instance pinning an older revision of the lineage to the new one), which `project.apply_update` applies. A package-scope part made again moves nothing by itself: the authored component that binds it is revised as usual. The same parameters at the same version under another `name` (a second MPN in the same package) make that part its own component: the existing part's component, symbol and binding are copied as new lineages named after it and published on the same package and footprint (`created: true`, a note naming the original); a part without a `name` is named by its generic family's label ("Chip resistor 0603") when its parameters read as one. The CLI (`stdio`) uses this request; the UI will build the same command. Over MCP both are catalog entries behind the verbs: `find` names them, `query library.generators` lists, and `apply` with `op: library.generate_part` makes a part (since the cut-over, S3).
- **`library.package_from_generator`** (core, Edit, generators 1.1): `{ draft, generate, replace?, terminals?, renumber? }`. Applies the package-scope `generate` (found when the project holds it), then gives the open working set's package draft and the footprint draft landing it the generated package's content: its terminals matched to the current ones by number (or by position, as asked), its pads and drawings with fresh identities landing them, its part file as the model, `PackagePlan` as the outcome. One undo step; a footprint with content is refused unless `replace`. The desktop's Change package… sends it.
- **`library.replace_body`** (core, Edit, generators 1.4), **`library.body_fit`** (session, Read) and **`library.make_body`** (session, Edit): see [A body for an existing part](#a-body-for-an-existing-part).
- **`library.generators`** (session, Read): the shipped modules (name, hash, a summary of the description: version, parameters, presets, scopes), the embedded modules with their versions, and each generated part with its key, result hash, version and state: `current` (the shipped module is its own or the same version), `update_available` (a newer version ships), `shipped_older`, `superseded` (a newer version already made the next revision of this part) or `not_shipped`. Over MCP the reply stays within a model's budget: unfiltered, each generator by name, families and preset keys; `{generator}` adds its parameters and rules with each preset by key, name and basis (`cited`, `cited_unverified`, `estimated`); `{preset: <key>}` gives that one preset's values, citation and note; `{detail: true}` every preset's.

## A body for an existing part

A placed part whose package has no body of its own (a project part of a board's own lands that no generator made) gets a generator's body while it keeps its footprint. The generator runs in package scope; only its body is used.

- **`library.body_fit`** (session, Read, generators 1.4): `{designator, generator?, preset?, params?, pins?, tolerance?, missing?}`. Without a generator it describes the part: its package (terminals, envelope, current model), the other placed parts that use the package, and its footprint's pads in the package's datum frame in millimetres. With one, the host evaluates the generator's part file (as `library.generate_part` does) and the reply is the plan `library.replace_body` would apply, changing nothing. `missing` instead of a generator is refused with that text (`body.no_generator`), so a workflow run ends with the reason no generator makes the body.
- **The fit.** Each of the generation's lead contacts lands the package terminal whose designation is its key, or the one `pins` (`[{lead, pad}]`) names. The contacts of each terminal, as one centre, are fitted onto the centre of its copper pads by a rigid 2D fit (`package_fit::fit_leads`, any turn, quarter turns exact), on the footprint of the part named; the model is then lifted by the generation's seating height. A plan is `accepted` only when every lead's contact lies on its land within the middle half across it (the board check's `package.lead_off_land` rule, `package_fit::lead_states`), within `tolerance` (0–0.5 mm, default 0), on every footprint the parts use. A lead without a pad, two leads on one pad and a body that lands better mirrored are blocking findings too. **Mechanical leads** (a connector's locating peg, a buzzer's alignment pin) land a non-plated hole: by `pins` `{lead, hole: <pad id>}` (the target lists each pad with its `id`), by `pad` naming a numbered hole, or, for a lead that lands no terminal, the free non-plated hole its contact lies in after the fit (generators 1.7). Explicitly mapped pegs take part in the fit; each must lie within its drilled outline plus `tolerance` (`body.peg_off_hole`). A peg is no package lead: the hole never gets a terminal or a net. The plan lists each lead's miss and distance from its pad's centre and, in `on_land` (generators 1.7), where its contact sits: the contact and the land's centre in the datum frame, its offset along the lead (positive outward from the package's centre) and across it (positive to the left of outward), the land's length and width, and the same in words; pegs carry their `hole`. Worst first, the copper pads no lead lands (reported only), the placement, the body before and after, and `change_counts`.
- **`library.make_body`** (session, Edit, generators 1.4): `{designator, generator, preset?, params?, pins?, tolerance?, sources, expected_revision}`. Applies `library.replace_body` with the evaluated part file and the provenance "3D body recreated by AI from ‹sources› with the generator ‹name›, preset ‹key›, fitted to the footprint's pads (the footprint kept). Reviewed: no."
- **`library.replace_body`** (core, Edit, generators 1.4): `{package, generate, pins?, tolerance?, provenance}`. Plans again and refuses a body that does not fit (`body.misfit`, naming each lead that misses), a lineage with a draft (`body.draft_open`) and one whose newest revision is not the one the parts use (`body.not_newest`). Otherwise, as one undo step: the part file becomes a Model (or the project's Model of the same bytes is reused); the package's next revision takes only the new model (its lead bodies bound to the pads they land), placement, envelope and lead contacts, with the provenance added to its own; every footprint of the bindings the parts use, those bindings and their components are republished pinning the new revisions, unchanged otherwise; every placed part that used the package moves to its component's new revision (`updates::move_instances`). Terminals, pads, bindings' mappings and the electrical definition never change. Outcome `BodyReplaced`: the new package revision, the model, the revisions published and the plan.
- **The review.** `library.review_check` with `body: <designator>` (library 3.4) holds a review report against the part's body instead of the drafts: the report's citations, and that the package's provenance records a recreation. Its Markdown is the body's review.
- **The workflow.** `library/assist/workflows/datasheet-to-body` runs these steps from datasheets ([workflow format](workflow-format.md)); `sparksmith-cli design-body` runs it headless ([development](development.md)).

## Checks on load

`sparksmith_io::read_project` (any full read of a container) runs, after the document's validation:

1. Structure (`library::generated::validate`, part of `Library::validate`): each record's revisions exist with the kinds of its scope, no revision is made by two parts, each key once per version, a bounded key-to-id map with each id once, ABI 1, and the module packed as `application/wasm`.
2. Every asset entry's bytes hash to the hash in its name. A mismatched entry that a record names as its module is refused in a generator's words.
3. For each part: compile its module once per hash, run the recorded request, and compare. The result hash must equal the recorded one, and the stored revisions must equal the expansion exactly.

A refusal leaves the open document as it was. The refusals:

| Code | When | Message (example) |
|---|---|---|
| `generated.module_changed` | The embedded module's bytes do not hash to the recorded hash. | the generator module embedded in this project for ‘Chip resistor 1.6 × 0.8 mm’ (r1) has been changed: the project records sha256 a5cf49bc…a1e3, but the embedded bytes hash to sha256 0c6d…. The project was not opened. |
| `generated.result_changed` | The module makes a different result from the recorded parameters. | ‘…’ (r1) was recorded as generator result sha256 ac6c…, but its embedded module now makes sha256 …. The project was not opened. |
| `generated.expansion_changed` | The stored revisions differ from the expansion. | ‘…’ (r1) stored in this project differs from what its generator makes from the recorded parameters: the stored part hashes to sha256 …, the generator's expansion to sha256 …. The project was not opened. |
| `generated.unverified` | The module refuses or fails under the limits. | ‘…’ (r1) could not be checked against its generator: *the host's refusal*. The project was not opened. |
| `generated.module_missing` | A record names a module the project does not embed. | the generator module sha256 … that made ‘…’ (r1) is not embedded in this project |
| `generated.record`, `generated.abi`, `generated.params` | A malformed record. | names the part and what is wrong |

Hashes in messages are written in full. The "stored part" hash is the SHA-256 over the stored revisions' canonical JSON in expansion order; the expansion hash is the same over what the module makes now. Both exist only to tell the two apart in a message.

`library.generate` adds `generated.module` (the hash is packed as something else), `generated.module_changed` (inline bytes do not hash to their name), `generated.module_missing`, `generated.params`, `generated.name` and `generator.runtime`, and passes the module's own refusals (`param.*`) and the host's (`generator.*`) through with their codes.

## A missing or changed module

- **Missing from the program** (the generator folder is gone, or a module is no longer shipped): nothing changes. The project's embedded copy makes and checks the part; `library.generators` reports the part as `not_shipped`.
- **Changed** (the program ships another module of the same generator, matched by the description's `id_hint`): the project keeps its embedded copy and its parts stay as they are, checked against that copy. Nothing is ever updated silently. When the shipped module is a newer version, `library.generators` reports `update_available` with both hashes; making the part again with it (`library.generate_part`, same parameters) publishes the next revisions of the same lineages (G15), carries the component's Parts to them and returns the update preview for the placed instances, including instances whose Part was carried. An older shipped version is `shipped_older` and is refused if used.
- **Embedded copy changed** (bytes edited in the file): refused on open, `generated.module_changed`.

## Gate: no built-in data

`cargo xtask no-builtin-data` (alias `no-builtin-parts`, in `cargo xtask ci`) parses every Rust file under `apps/` and `crates/` and fails on `include_str!` or `include_bytes!` in non-test code, nested macros included. Test code is skipped: items under a test-only `cfg` (`test`, the `test-fixtures` feature), `#[test]` functions, files a test-only `mod` declares, and `tests/` and `benches/` folders. Generator crates are not scanned: their presets are the module's own data.

The allowlist (`xtask/src/no_builtin_data.rs`) names a source file and an included path for each entry:

- interface assets: the IBM Plex fonts and the blur shader (`crates/ui`);
- the MCP skill prompt (`crates/automation/src/mcp/prompts.rs`).

The generator modules replace the starter package rows.

An entry that matches nothing fails the gate, so each is removed with the data it allowed.

## Decode bounds

The integer-only canonical codec accepts at most 64 nesting levels, 524,288 total JSON values plus object keys, and 1 MiB of decoded UTF-8 across all keys and string values. The existing caller byte limits still apply (64 KiB request, 256 KiB description, 1 MiB response). Each structural node and decoded string byte is charged before its allocation; keys are checked with a tree set before their values are read, including duplicates written with different JSON escapes. Object order and canonical output bytes are unchanged.

The new node/text budgets admit every JSON tree already accepted under the existing depth limit and 1 MiB response bound: a tree with `n` charged nodes needs at least `2n - 1` wire bytes, and JSON escape decoding never increases string byte length. A caller allowing larger wire input still receives an explicit codec refusal at the structural/text limits. The host applies the same decoder to descriptions, generations and error reports, after module execution; this work is not charged to WASM fuel. Tests cover the densest tree fitting 1 MiB, decoded duplicate keys, a 60,000-key map, maximal pad count, and worker permits retained through timeout/cancellation and result destruction. Timing measurements are evidence for a stated host, not assertions in the tests. A busy description remains a typed transient failure: it is not recorded as an invalid module or cached as an incomplete catalog. The app shelf retries in the background only when a view requests it after a 250 ms backoff; dropping or replacing the shelf abandons its results and retry state. A session search retries its uncached descriptions on the next request. Permanent module refusals keep their existing presentation; making a part reports busy and can be submitted again.

Parallel tests explicitly inject a fixture runtime whose clones share their own four-worker pool; unrelated fixture sessions cannot consume it. `Worker::default` and `Worker::new` always use the production process pool, even when the test-fixtures API is compiled in. Sessions reuse the runtime installed on their engine, including when lending or forking it. Dedicated worker tests exercise both the actual process pool across fresh workers and shared fixture pools; no suite-wide serialization or larger cap is used.

## Limits of GP1

- **Fields.** A generation's `component.fields` (standard field keys such as `value`) and derived `fields` stay in the generation and its result hash, and the host does not read them. A component-scope part of a generic family (the shipped `catalog/generic-families.json`, matched by generator and the family's preset parameters) selects the family's standard `fields`, shown on the symbol, and its `value_template`, from the project's copies of the standard fields (imported with the part); any other component-scope part selects the standard part value field `Value`, a text field shown on the symbol. These are host data outside the generation: the load check keeps the stored selection and compares the rest.
- **Package geometry.** The package keeps the generation's envelope and the generator's part file (GP2), the seating height as the model's lift, and its lead contacts (see "Lead contacts on the package"). No footprint polarity is set from pin 1.
- **Part-file bodies and terminals**: see slice B2 below.
- **The chip part files' overcoat inset** is 0.04 mm, a literal in the saved file; it does not narrow below 0.16 mm of body width, which no chip preset reaches.
- **Arcs** (since B3) carry exact ends: `Arc { center, start, end, clockwise }`; the module computes them (the SDK's `draw::arc`, integer trigonometry) and the host does no trigonometry.
- **Bundles.** Promoting a generated part to a library folder copies its revisions without the record; the folder copy is an ordinary part.
- **Load cost.** Every open runs each part once: about 4 ms to compile a module and 1–2 ms per part (GP0's measurements), so a project with 100 generated parts adds roughly 0.2 s. A cache keyed by part key and result hash is the next step if that grows.

## Lead bodies carry terminals (slice B2, 14 November 2026)

A part file names no terminal. When a package is given a part file, the host binds each body of a lead material (role `termination`) to the package terminal whose lead contact lies under it (within 10 µm in x and y, `part_file::lead_bodies`) and stores the binding with the derived data (`PartDerived::leads`, by terminal designation). The contacts are a generated package's lead contacts (`library.generate_part`: a contact under no lead body, or a body under contacts of two terminals, is refused) or the centres of the pads of the package's footprint (`library.use_part_file`, `library.set_part_values`: such a pad is skipped and such a body left unbound). Every board build gives those bodies their terminal, so they highlight and pick with their nets; packages with the same file and values share a model definition unless their bindings differ. Nothing is added to Solidcraft. Measured: the WROOM-3 part file used on the example's package binds its pad bodies (`the_wroom3_pad_bodies_bind_to_their_pads_terminals`).

## File version 3 (14 November 2026)

Slices B1, B3 and B4 change what a project stores: the record (generator id, version, bundle, key-to-id map) and part-file values as integers (`PartValue`: `nm`, `mdeg`, `count`, `milli`).
